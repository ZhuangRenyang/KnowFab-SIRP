# DH-15 OEE 完整版 —— 设计规格

> 真 OEE = 可用率 × 性能 × 良率。
> 现在系统只有「稼动率」（运行 ÷ 已记录时长），差两个客户还没给的数据：**标准产能**和**不良数**。
> 本次把 OEE 做成**完整的三因子引擎**，客户数据不全时**明确说差哪一项**，绝不拿半成品冒充完整 OEE。

---

## 1. 三个因子的口径与数据来源

| 因子 | 标准定义 | 本系统怎么算 | 缺什么 |
|------|----------|--------------|--------|
| **可用率 A** | 运行时间 ÷ 计划生产时间 | `prod_hourly.run_sec` ÷ **周期内班次总时长** | 无（班次方案已有） |
| **性能 P** | 实际产量 ÷ 理论产量（理想节拍 × 运行时间） | 实际产量 ÷ (`run_sec` ÷ 理想节拍) | **理想节拍**（设备配置，秒/件） |
| **良率 Q** | 良品数 ÷ 总产出 | (总产出 − 不良数) ÷ 总产出 | **不良数**（自动采集 / 人工补录） |

**OEE = A × P × Q**，任一因子算不出来 → OEE 也算不出来（显示 `--`，并说明缺什么）。

### 1.1 为什么可用率的分母是「计划生产时间」而不是「已记录时长」

现有的「稼动率」= 运行 ÷ 已记录时长，回答的是「**这段有记录的时间里**有多少比例在跑」。
OEE 的可用率 = 运行 ÷ 计划生产时间，回答的是「**该干的活**干了多少」。

两个数会不一样，差的那部分就是损失（没接上设备、非计划时段），正是 OEE 要抓的东西。
报表上两个数并存，各自带分母说明，不互相覆盖。

### 1.2 理想节拍（秒/件）——按设备配置

- 存在 `device.ideal_cycle_sec`（可空，NULL = 未配置）
- 客户填「状态最好时加工一件要多少秒」，车间主任给一个数就行；换产品时自己改
- **为什么不用「日产量目标」（`daily_target`，已有字段）倒推**：日目标是按全天算的，
  设备只跑半天时倒推出的节拍会偏大，性能率算出 >100%，看着像 bug。
  工艺节拍没有这个问题，它跟班次长度无关。两个字段在表单里各自写清区别。
- **性能率可能 >100%**：说明理想节拍配小了。**不截断**，如实显示并给提示——
  截断会把「节拍配错了」这个信息藏起来。

### 1.3 不良数 —— 两条路

| 来源 | 怎么来 | 适用 |
|------|--------|------|
| **自动采集** | 点表新增 `role=reject`（不良品计数）角色，机床的不良品计数器直接采 | 机床有这个计数器 |
| **人工补录** | 复用现有「产量补录」表单，加一列「不良数」（按天×设备） | 机床没有计数器 |

两条路的数会**汇总**（自动的按小时 + 人工的按天）。

### 1.4 「不良数有没有数据」怎么判定

不是「不良数 = 0 就说明没不良」——那会把「没采到」和「真的零不良」混为一谈。

判定规则：
- 设备**配了 `reject` 点位** → 自动有数据（即使本期是 0 件，也是**已知的 0**）
- 本期**有不良数补录记录** → 人工有数据
- 两者都没有 → **不良数数据缺失**，良率算不出来

## 2. 数据模型

| 表 | 新增字段 | 说明 |
|----|----------|------|
| `device` | `ideal_cycle_sec` DOUBLE NULL | 理想节拍（秒/件） |
| `prod_hourly` | `defect` DOUBLE NOT NULL DEFAULT 0 | 该小时的不良数（自动采集） |
| `manual_entry` | `defect` DOUBLE NOT NULL DEFAULT 0 | 人工补录的不良数 |

迁移脚本 `1.5.0.sql`：走项目既有机制（jar 内置、幂等、不阻断启动），`information_schema` 守卫 + `DO 0`。

## 3. 计算引擎：`report/OeeCalculator`

```java
OeeResult compute(OeeInput in)
// in:  runSec, output, defect, hasDefectData, idealCycleSec, plannedSec
// out: availability / performance / quality / oee（Double，null = 算不出来）
//      plannedSec, theoreticalOutput, notes（人话说明，缺什么、怎么补）
```

**notes 用人话写**，前端直接显示，例如：
- 「没配理想节拍，性能算不出来。到设备配置里填「理想节拍（秒/件）」」
- 「没有不良数数据，良率算不出来。机床有不良品计数器就配一个 role=reject 的点，没有就用补录录一下」

## 4. 报表输出

```json
"oee": {
  "availability": 62.5,
  "performance": null,
  "quality": null,
  "oee": null,
  "plannedSec": 86400,
  "runSec": 54000,
  "output": 281,
  "defect": null,
  "hasDefectData": false,
  "idealCycleSec": null,
  "notes": ["……"]
}
```

- 总量（totals）：按全部设备汇总。**注意**：多台设备用各自的节拍算性能率，
  汇总性能率 = Σ实际产量 ÷ Σ各设备理论产量（不能把百分比平均）
- 每台设备（byDevice）：各自一套因子
- 日报：计划生产时间 = 当天班次总时长
- 月报/区间：计划生产时间 = 周期内每天班次总时长之和

## 6. 测试

### 6.1 单元测试（`OeeCalculatorTest`）
- 三个因子齐全 → OEE = A×P×Q
- 缺理想节拍 → 性能 null、OEE null、notes 说清缺什么
- 无不良数据 → 良率 null、OEE null
- 有 reject 点位但本期 0 不良 → 良率 100%
- 运行时间 0 → 可用率 0、性能 0（不是 NaN）
- 计划生产时间 0（没配班次）→ 可用率 null（退回已记录时长口径并标注）
- 理论产量 0（节拍为 0）→ 性能 null

### 6.2 selftest 新增 L 组
- 理想节拍能存能读回
- 不良数补录能存，报表的 defect 汇总对
- OEE 三因子齐全时数值正确
- 缺项时 OEE 为 null 且 notes 说清缺什么

## 7. 明确不做

- ❌ 不做「计划产量」口径（用户已确认用理想节拍）
- ❌ 不把 dailyTarget 倒推成节拍（会算出 >100% 的性能率）
- ❌ 不做 OEE 历史趋势图（先让数算对）
- ❌ 不做按产品的节拍（系统没有产品/工单维度）
- ❌ 不改现有「稼动率」的口径（两个数并存，各带分母说明）
