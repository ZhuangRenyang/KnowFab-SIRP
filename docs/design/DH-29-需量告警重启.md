# DH-29 需量告警重启丢失 —— 设计规格

> 问题：客户「昨天超合同需量」的告警，一重启就查不到了。
> 根因：需量告警 `r-demand-over` 由需量模块直接写 `alarm_event`，**规则不在 `alarm.rules` 里**；
> `AlarmEngine.restore()` 重启时按规则表找对应规则，找不到就把未恢复告警自动关掉，
> 关闭理由写「规则已删除或停用」——**规则根本没被删过，这是假话**。

---

## 1. 现状（已核实）

| 事实 | 位置 |
|------|------|
| 需量告警规则 ID `r-demand-over`，直接写 `alarm_event`，不走 `alarm.rules` | `demand/DemandMonitor.java:40` |
| 告警的 `deviceCode` 是 `PLANT`（全厂），**不是一个真实设备** | `DemandMonitor.java:41` |
| 通知时临时 new 一个 `AlarmRule` 只为传给 notifier | `DemandMonitor.java:132` |
| 重启时规则找不到 → 自动关闭，理由「规则已删除或停用」 | `alarm/AlarmEngine.java:166` |
| 正常运行时也有同样的误伤：设备不存在 **或** 规则不在表里 → 关闭 | `alarm/AlarmEngine.java:580` `cleanupOrphans()` |
| **实测数据**：198 条需量告警中 **196 条**被「规则已删除或停用」关掉，只有 1 条是真正的「需量已回落到合同范围内」 | 生产库 `alarm_event` |

**双重误伤**：`cleanupOrphans()` 每个评估周期（2 秒）都在跑，`PLANT` 不在设备表里、`r-demand-over` 不在规则表里，
**两个条件同时命中**。所以只改 `restore()` 修不干净。

## 2. 核心设计决策

### 2.1 引入「系统告警」这个概念

不是所有告警都来自用户配的规则。有些是系统模块自己产生的（目前只有需量），它们的规则**本来就不在规则表里**，
生命周期由产生它的模块自己管。

- 单一来源：`alarm/SystemAlarms.java`，登记系统规则 ID
- `AlarmEngine` 只认这个名单，不认识具体是哪个模块 —— 以后再有系统告警，加一行就行
- `DemandMonitor` 引用 `SystemAlarms.DEMAND_OVER`，避免字符串两处各写

### 2.2 为什么不用路线图里的①「把需量规则注册进 alarm.rules」

需量规则的**真正配置**（合同需量、预警比例、开关）在 `AppSetting("energy.demand")` 里，
告警规则表是给用户配阈值用的。把它塞进 `alarm.rules` 会导致：
- 用户能在规则列表里看到并编辑它，改了却不起作用（改的是另一份配置）
- 删掉它，需量告警就哑了
- 要额外做「系统规则分组」的 UI（用户能不能编辑？能不能停用？都得定义）

**结论**：注册进规则表是把「用户配置」和「系统配置」搅在一起。系统告警就该有自己的通道。

### 2.3 为什么不用路线图里的②「restore() 对没有对应规则的告警一律保留」

太宽：用户**真删了规则**时，那条规则的告警就会永远挂着（没人能确认、也没人知道它为什么还挂着）。
路线图里也标了这个风险。

**结论**：只对**登记在册的系统告警**开豁免口子，用户规则维持原样（删规则 → 关告警）。

## 3. 改动清单

### 3.1 `alarm/SystemAlarms.java`（新增）
系统告警名单与判定：`DEMAND_OVER = "r-demand-over"`、`isSystem(ruleId)`。

### 3.2 `alarm/AlarmEngine.restore()`
规则找不到时：
- **系统告警 → 保留**并放进 `open` 继续跟踪（不关闭、不改状态、不动 startedAt）
- 其它告警 → 照旧关闭，理由「规则已删除或停用」（用户规则被删/停用，这句话是真的）

### 3.3 `alarm/AlarmEngine.cleanupOrphans()`
系统告警**整体跳过**：它既没有设备也没有规则，两个「孤儿」判断对它都不成立。

### 3.4 `demand/DemandMonitor`
- 需量监控被关闭、或合同需量清零时，把挂着的需量告警收掉，理由「需量监控已关闭」
  （否则系统告警会永远挂着——豁免了 restore 的关闭，就必须有人负责关它）
- 需量仍在超限 → 不新增（保持现状）
- 需量已回落 → 关闭，理由「需量已回落到合同范围内」（保持现状）

### 3.5 历史数据修正
196 条需量告警的关闭理由是**假的**（「规则已删除或停用」）。这个理由由 `restore()` 独占，
所以「被这句话关掉的需量告警」= 「被系统重启关掉的需量告警」，可以无歧义地识别。

改成诚实说法：`系统重启时自动关闭（当时是否已回落在历史数据中无法追溯）`

只改 `rule_id = 'r-demand-over'` 的，其它规则被同样理由关掉的那 1 条**不动**（那条是真·规则被删）。

## 4. 重启后的完整行为

| 场景 | 行为 |
|------|------|
| 重启时需量仍超限 | 告警**保持 ACTIVE**，startedAt 不变（追溯完整），**不新增第二条** |
| 重启时需量已回落 | DemandMonitor 下一轮（30 秒内）关闭，理由「需量已回落到合同范围内」 |
| 重启时监控被关 | DemandMonitor 关闭，理由「需量监控已关闭」 |
| 用户删了普通规则 | 不变：告警关闭，理由「规则已删除或停用」（真话） |

## 5. 测试

### 5.1 单元测试（新增）
- `AlarmEngineRestoreTest`：系统告警在重启时被保留（且进了 `open` 继续跟踪）；
  普通规则缺失时仍被关闭，理由不变

### 5.2 selftest 新增 K 组
- 需量链路端到端：合同需量调低 → 出现 ACTIVE 的需量告警 → 规则表里**没有**这条规则（证明它确实是系统告警）
- 关闭需量监控 → 告警被关闭，理由是「需量监控已关闭」而**不是**「规则已删除或停用」
- 恢复配置 → 重新产生告警
- 测完还原配置

### 5.3 人工实测（重启）
起实例 → 造一条超需量告警 → **重启实例** → 验证：
- 告警还在、startedAt 没变、仍然只有一条
- 日志里没有「因规则失效自动关闭」

## 6. 明确不做

- ❌ 不改 `system.schemaVersion`（无表结构变更）
- ❌ 不动 `alarm.rules` 的用户规则逻辑
- ❌ 不做需量告警的自动动作（自动停机/推单）
- ❌ 不碰 DH-28 停机原因录入
- ❌ 不改需量配置的存储位置（仍在 `AppSetting("energy.demand")`）
