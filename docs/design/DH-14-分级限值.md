# DH-14 告警限值分级 —— 设计规格

> 目标：**同一测点可配多级限值（预警→告警→停机），触发只报最高级**，减少误报疲劳。
> 一句话：现在是「一个测点一个阈值」，配三次就报三次；分级后配一次，只报最严重的那档。

---

## 1. 现状（已核实）

| 事实 | 位置 |
|------|------|
| 规则模型已有 `level` 字段（MAJOR/MINOR/CRITICAL），但**规则编辑界面根本没暴露它**，用户永远拿默认 MAJOR | `AlarmRule.java:66`、`frontend/src/views/AlarmView.vue`（`rule.level` 未绑表单） |
| 引擎按 `(ruleId, deviceCode)` 建键开告警，每条规则独立触发 | `AlarmEngine.evaluate()` |
| THRESHOLD 判定只用「规则级 op + 单一 threshold」 | `AlarmEngine.sample()` 的 `TYPE_THRESHOLD` 分支 |
| 等级已经是一等概念：通知配色、免打扰按级过滤、列表筛选、大屏色条 | `AlarmNotifier`、`ScreenService`、`fault.html` |
| 大屏用**中文字符串**判等级（`levelText==='严重'`），改文案就会坏 | `static/fault.html:319` |

## 2. 核心设计决策

### 2.1 为什么是「一条规则带多档」，不是「多条规则靠引擎分组」

考虑过两种做法：

- **甲：用户建 3 条规则（同一个测点，阈值 80/85/90），引擎按 (设备,测点) 分组只报最高级**
  - 优点：规则结构不变、零迁移
  - **致命缺点：静默失效。** 只要用户把某条规则的 `pointKey` 打错一位，它就分不进组，
    3 条告警全冒出来，而界面上没有任何提示解释为什么。分组是「引擎猜出来的」，用户看不见。
- **乙：一条规则内配置多档限值（档位列表），一条规则 = 一个测点 = 一条告警**
  - 优点：分级是**规则自己的属性**，用户看得见、改得对；不存在跨规则干扰；一条规则天然只产生一条告警
  - 代价：规则 JSON 多一个 `tiers` 字段（老规则为空 = 老行为，零迁移）

**定：走乙。** 误报疲劳的根因是「用户表达不了分级意图」，那就让规则能直接表达分级，
而不是让引擎去猜哪些规则是一组。

### 2.2 数据模型

```java
public class AlarmRule {
    // ...现有字段不动...
    /** 多级限值：同一测点的预警/告警/停机三档。空 = 老规则，用单值 threshold + level */
    private List<Tier> tiers = new ArrayList<>();

    public static class Tier {
        private String level = "MINOR";   // MINOR 预警 / MAJOR 告警 / CRITICAL 停机
        private Double threshold;
    }
}
```

- 规则级 `op`（`>` `>=` `<` `<=` `==` `!=`）对**所有档位统一**——一个测点的越限方向是同一个
- **老规则（`tiers` 为空）= 隐式单档（`rule.level` + `rule.threshold`）**，行为与今天 100% 一致
  - 存量客户机上的规则 JSON 不需要迁移，`AlarmRuleStore` 不用改存储格式
- 等级顺序：**MINOR < MAJOR < CRITICAL**

### 2.3 判定（`AlarmEngine.sample()` 的 THRESHOLD 分支）

1. 取点位值 `v`；无值/坏值 → 本轮不判断（返回 null，和今天一样，绝不误报）
2. 用 `op` 逐档比较，得到命中的档位集合
3. 取**等级最高**的命中档 → 即「当前档位」
4. 一个都没命中 → 本轮正常（ok）
5. 命中 → bad，并携带该档的 `level` + `threshold`

> **只有一条规则 → 只有一条告警**，这是模型自带的保证，不需要引擎做任何分组。

### 2.4 事件等级与「换档」

| 场景 | 处理 |
|------|------|
| 事件首次创建 | `level`/`threshold`/`message` 取自命中的最高档 |
| 事件开着，档位**升**了（等级更高） | **就地换档**：更新 `level`/`threshold`/`message`，**不新增事件**；按冷却发一条「升级为 X」通知 |
| 事件开着，档位**降**了 | **就地换档**：更新 `level`/`threshold`/`message`，**不发通知**（降级不是紧急信息） |
| 全部档位都不再命中 | 走现有恢复流程（`recoverSeconds` 后清除 + 发恢复通知） |

**关键约束：换档绝不产生第二条告警事件。** 事件数量始终 ≤ 1。

### 2.5 校验（`AlarmRule.validate()`）

新增：
- `tier.threshold` 不能为空
- `tier.level` 必须是 `MINOR`/`MAJOR`/`CRITICAL` 之一
- 同一规则内 `level` 不许重复（避免同档歧义）
- **档位阈值必须单调**：
  - `op` 为 `>`/`>=` 时，等级越高阈值应**递增**（预警 80 / 告警 85 / 停机 90）
  - `op` 为 `<`/`<=` 时，等级越高阈值应**递减**（预警 10 / 告警 5 / 停机 0）
  - `op` 为 `==`/`!=` 时**不允许配多档**（等值型没有递进意义）
  - 配反了就是「该报的级别不对」，属于危险配置 → **直接拒绝并说明哪两档反了**

老规则（无 tiers）走原有校验分支，行为不变。

### 2.6 等级文案（全局统一）

| 枚举 | 中文 | 英文 |
|------|------|------|
| MINOR | 预警 | Warning |
| MAJOR | 告警 | Alarm |
| CRITICAL | 停机 | Critical |

改动点（**4 处，缺一不可**）：
1. `AlarmNotifier.levelText()` —— 通知标题与恢复消息
2. i18n `alarmDict.lv.*`（列表标签）+ `alarmDict.levelOpt.*`（筛选下拉），中英各一份
3. **`static/fault.html:319` 改判枚举 `level`，不再比较中文字符串**
   —— 顺手修掉原有脆弱点：数据源 `ScreenService` 本来就同时给了 `level` 和 `levelText`
4. 规则表单里的等级下拉（走 i18n）

## 3. 前端

### 3.1 规则表单的限值区

改成「**档位列表**」：每行 = 等级下拉 + 阈值输入框（+ 单位只读展示），可增删行。

- **老规则打开编辑时自动展开成一行**（level + threshold），保证 100% 兼容、不丢数据
- 表单里现有的「单值阈值 + 等级」两个字段在多档模式下并入档位列表，不再单独出现
- 保存的 JSON：配了多档 → `tiers` 有值；只配一档 → 也写进 `tiers`（统一），
  但**后端必须继续接受并正确处理 `tiers` 为空的老格式**

### 3.2 展示

- 告警列表：等级标签 + 等级筛选下拉文案同步（预警/告警/停机）
- 规则列表：限值列展示成「预警 >80 / 告警 >85 / 停机 >90」
- 中英文都要有，**中英词条逐 key 对称**

## 4. 审计

规则新增/修改/删除本来就有审计（`AlarmController.saveRule` → `audit.ok(CAT_ALARM, ...)`）。
**detail 文案要体现档位**，例如：
- 新增：`新增告警规则 主轴温度（数值越限，点位 temperature，档位：预警>80 / 告警>85 / 停机>90，持续 60 秒）`
- 修改：`修改告警规则 主轴温度（档位由 预警>80 / 告警>85 改为 预警>80 / 告警>88 / 停机>90）`

**绝不记录任何密钥类字段**（本功能没有密钥，但要保证 detail 里只有档位和阈值）。

## 5. 测试

### 5.1 JUnit 单元测试（新建 `src/test/java/`，项目首批单测）

`spring-boot-starter-test` 已在 pom 里（JUnit 5 可用），但 `src/test` 目前是空的。

必须覆盖：
- 档位解析：各 op × 各取值的组合（`>`/`>=`/`<`/`<=`）
- 命中多档时取等级最高的那档
- 一档都没命中 → 不报警
- 老规则（无 tiers）走隐式单档，行为与今天一致
- 校验：缺阈值 / 等级非法 / 同档重复 / 阈值不单调（正反两个方向）/ `==` 配多档
- 换档：升档更新等级、降档更新等级、换档不产生第二条事件

### 5.2 selftest 新增 J 组（HTTP 级回归）

- 带 `tiers` 的规则：存得下、读得回、结构一致
- 4 种非法配置被拒（缺阈值 / 同档重复 / 阈值不单调 / `==` 配多档）
- 老规则（单值）保存后读回结构不变、行为不变
- **端到端分级**（核心断言）：
  - 在 sim 设备（CNC-01 有 `temperature` 点，℃）上配三档规则，`forSeconds=0`
  - 等设备有数后，查告警列表
  - 断言：**同一设备同一测点最多只有一条未关闭告警**（不是三条）
  - 且该告警的等级 == 按**读到的当前温度**算出的最高命中档
  - sim 温度是随机游走（30~85℃），所以断言必须按实测温度计算，不能写死档位
  - 用完必须清理规则和告警（自测脚本要自清）

## 6. 明确不做（边界）

- ❌ 不做自动停机 / 自动动作
- ❌ 不做跨规则的告警抑制（点错了点位也不会被「猜」回来）
- ❌ 不改 DH-29（需量告警重启丢失），那是独立议题
- ❌ 不碰 ERP 侧告警
- ❌ 不做告警风暴合并策略改造
- ❌ 不改 `system.schemaVersion`（无表结构变更）
