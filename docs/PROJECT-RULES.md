## R1 管理员初始账号密码（2026-11-04 定）

### 规矩

- 账号**永远**是 `admin`
- 密码**永远**是 `123456`
- 密码**存进数据库**（`sys_user` 表）
- **永远不要随机生成密码**
- **永远不要把密码写进任何文件**——`INITIAL_ADMIN.txt`、`data/initial-admin.txt` 一律**不生成**

### 为什么是这三条

1. **现场习惯就是先试 `admin` / `123456`。** 随机密码要客户翻文件，
   装机师傅经常卡在这一步（2026-11-01 实测反馈）。
2. **随机密码写文件后反而登不进去。** 应用启动时发现库里已有 admin 就**不会**改密码
   （那是保护客户已改密码的设计），于是文件里那份随机密码**永远无效**——
   客户重装一次就以为系统坏了。
3. **两个来源迟早对不上。** 文件里一份、数据库里一份，谁是真相说不清。
   只有一个真相来源（数据库）才不会出这种事。

### 执行范围（缺一不可）

| 位置 | 要求 |
|---|---|
| `install.sh` | 写 `system.admin.password: "123456"`；装完用应用自带的 `DEVICEHUB_RESET_ADMIN=1` 机制**一次性**同步进数据库；**不生成任何密码文件** |
| `deploy.sh` / `deploy-cn.sh` | 部署完直接打印 `admin / 123456`；**不读密码文件**（应用早就不写了） |
| 应用 `UserService` | `system.admin.password` 为空时兜底 `123456`；**不生成密码文件** |
| 发行包 `dist/*.zip` | 打包时必须带上上述脚本的**当前版本**（不能出现旧脚本） |
| 文档 | README / HANDBOOK 统一写 `admin / 123456`，不留"随机生成"的旧说法 |

### 配套要求

- **上线前必须改密码。** 系统在登录后提示，改密码时强制 ≥8 位。
  固定密码意味着门一直开着——客户现场装上就忘改，等于没设密码。
- **同步只做一次。** `DEVICEHUB_RESET_ADMIN=1` 用一次性 systemd drop-in，
  启完立刻撤掉 → 之后再重启**不会**重置，客户改过的密码得以保留。

## R4 数据库默认账号密码（2026-11-04 定）

### 规矩

- 数据库默认登录账号 **`admin`**，默认密码 **`123456`**
- **不随机生成数据库密码**
- 与管理员密码一样：**永远不要写进任何密码文件**
- 用户/客户在系统后台改自己的密码

### 为什么和 R1 一样处理

一开始数据库密码是随机的（`deploy.sh` 生成 `.env` 写 `sirp_<随机>`，
便携版 `start.sh` 生成 16 位随机串）。问题很实际：

- 客户拿到包不知道数据库密码 → 要翻文件、要问人
- 现场实施经常卡在这一步
- 随机密码**没法记在交付单上**，也没法口头交接

固定 `admin` / `123456` 之后，**交付单上能直接写**，
装机师傅照着敲就行。安全风险用交付流程兜：
上线前在系统后台改密码（管理员密码），
数据库密码需要更强时用 `--db-pass` / `.env` 覆盖。

### 执行范围

| 位置 | 要求 |
|---|---|
| 应用 `application.yml` | `username: ${DEVICEHUB_DB_USER:admin}`、`password: ${DEVICEHUB_DB_PASSWORD:123456}` |
| `install.sh` | `DB_USER="admin"`、`DB_PASS="123456"`（`--db-pass` 可覆盖，不再必填） |
| `docker-compose.yml` | `MYSQL_USER: ${DB_USER:-admin}`、`MYSQL_PASSWORD: ${DB_PASSWORD:-123456}` |
| `deploy.sh` / `deploy-cn.sh` | `.env` 写 `DB_USER=admin` / `DB_PASSWORD=123456`；**删掉 `rand_hex` 随机生成** |
| `tools/portable/start.sh` | `PWD_DB="123456"`；`CREATE USER 'admin'@...`；**删掉随机生成与其注释** |
| 前端「数据库密码」面板 | 默认账号/密码提示改成 admin / 123456 |
| 测试脚本 | `qc-gate.py` / `qc-e2e.py` / `upgrade-drill.py` 的默认账号密码同步 |

### 数据库名不在这条规则里

库名固定 `devicehub`（原来 install.sh 默认写的是 `device_hub`，
和 application.yml / docker-compose 不一致——已统一）。

## R2 计量口径只定义一处（2026-11-04 定）

- 全系统只有 `MeterScope` 一个地方定义"某范围的电量/需量该怎么加"。
- 需量与电量**必须用同一套规则**——否则同一个页面上「需量按总表算、电量按所有设备算」，
  用户会发现两个数对不上。
- 口径缺失要能被看见：返回里带 `meterMode` 之类的标记，界面据此提示。

### R2b 库存口径只定义一处：单据汇总（2026-11-05 定，DH-80）

- 库存余额 = `erp_stock_bill` 明细累计（`voided_at is null`）。
  定义处：`ErpStockBillRepository.aggregateStock()`。
- **「未过账增量（pending）」不是库存**：它记的是原始总产出（含不良），
  而单据写的是良品量——混进余额会让客户看着库存「掉一批不良数」；
  且它在 JVM 内存，`FOR UPDATE` 锁不住，混进可用量会超卖。
  ⇒ 只作提示，由 `balances[].pendingQty` / `summary.pendingTotal` 单独返回。
- **校验层与承诺层绝不看 pending**：出库校验、盘点差异基准、销售可承诺量
  必须只认单据汇总（与落库同源 + 行锁），否则超卖。
- `summary.stockMode = "BILL"` 正向声明口径（同 `meterMode` 的范式）。

## R3 交付前必须过真机（2026-11-04 定）

- 交付物的门禁不能只测「包对不对」，还要测「**装完能不能用**」。
- 交付链路是四层，**每一层都要查**：

  ```
  代码 → 打包 → 安装 → 审计
  ```

  前一层查了不等于查全了（2026-11-04 就漏过「打包层查了、安装层没查」，
  客户机上 backup.sh 根本不存在）。
- 装完要**逐个检查产物在不在**，缺了就 warn，不能静默跳过。
- 打包用的 jar 必须是**当前代码**编出来的：打包前断言 jar 比所有源文件新。
