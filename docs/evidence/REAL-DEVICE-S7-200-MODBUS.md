# 真机验证：西门子 S7-200 SMART（Modbus TCP）

> 日期：2026-11-06
> 设备：西门子 S7-200 SMART，IP `192.168.10.1`，以太网口直连测试电脑
> 被测代码：Spring Boot **4.1.2**（`upgrade/boot-41` 分支）
> 配套文档：[OPC-UA-BOOT4.md](OPC-UA-BOOT4.md)（同一次升级的 OPC UA 侧验证）

---

## 1. 结论

**项目自己的 Modbus TCP 驱动在 Spring Boot 4.1.2 下能连上真实工业设备并读到实时值。**

```
code=REAL-S7-200  protocol=modbus-tcp  host=192.168.10.1  port=502  online=True
  寄存器 40000   value=16384   quality=GOOD
  寄存器 40001   value=5632    quality=GOOD
  寄存器 40020   value=0       quality=GOOD
  寄存器 40021   value=0       quality=GOOD
```

应用日志：

```
[REAL-S7-200] 采集启动，协议=modbus-tcp，点数=4，周期=1000ms
[REAL-S7-200] 已连接
```

> **为什么这条链路重要**：OPC UA 那侧是用 milo 本地 server 验的（真机 S7-200 不支持 OPC UA）。
> 而 Modbus TCP 是**这个设备在现场的默认通路**，也正是 `docs/README.en.md` 里
> 「Direct Ethernet | `modbus-tcp` | … e.g. Siemens S7-200 SMART」写的那一条。
> ⇒ 升级后**两条工业协议路径都验过了**：一条真机、一条真协议本地 server。

## 2. 设备侧事实（现场知识，最容易丢的部分）

### 2.1 Modbus TCP 只允许 1 个客户端连接

S7-200 SMART 的 Modbus TCP 服务器**同时只接受一个客户端**。

⇒ **应用采集器占着连接时，任何第二个客户端连上去都会被重置**：
```
ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接
```

⚠️ **看到这个报错不要以为设备坏了** —— 现场排查时极易误判成「PLC 挂了 / 网线松了 / 服务停了」。
真实原因是「连接数满了」。

⇒ 推论：**这个设备现场只能接一套采集系统**。如果客户还要接组态软件 / SCADA，
需要提前规划（这是设备限制，不是我们系统的限制，但客户会当成我们的问题报上来）。

### 2.2 有效地址区

| 起始地址 | 结果 |
|---|---|
| 0 | 可读，全 0 |
| 100 / 1000 / 2000 / 4000 / 10000 | **异常码 2（非法地址）** |
| **40000** | **可读，有数据** |
| 40001 | 可读，被 PLC 程序持续写入（值在变） |

⇒ 有效区在 **40000 起**（4xxxx 编号段）。

### 2.3 四种功能码都正常

`0x03` 读保持寄存器 / `0x04` 读输入寄存器 / `0x01` 读线圈 / `0x02` 读离散输入 —— 全部正常应答。

### 2.4 寄存器语义

- `40000` = **常量 16384**（一直不变）
- `40001` = **被 PLC 程序持续写入**（实测 5120 → 5632 → 16640 → 21760）
- `40020` / `40021` = 也是程序维护的量（实测 21504/5120 → 0/0 → 21504/21760）

⚠️ **被 PLC 程序写入的寄存器不要拿来做上位机写入测试**（见 §4）。

## 3. 验证方法（可复现）

### 3.1 环境

| 项 | 值 |
|---|---|
| 设备 | S7-200 SMART，`192.168.10.1:502`，unitId=1 |
| 测试电脑网口 | 「以太网」= `192.168.10.100/24`（静态 IP，与设备同网段） |
| 应用 | `device-hub` 1.0.29（Spring Boot 4.1.2），端口 8081，隔离库 `devicehub_verify` |

给测试电脑加静态 IP（**非管理员加不了**，`netsh` / `New-NetIPAddress` 都会被拒）：

```powershell
New-NetIPAddress -InterfaceIndex 13 -IPAddress 192.168.10.100 -PrefixLength 24
```

### 3.2 协议层探测（不启动应用）

`tools/probe-modbus.py` —— 现场排查用，进仓库：

```bash
python tools/probe-modbus.py 192.168.10.1          # 连通性 + 四种功能码
python tools/probe-modbus.py 192.168.10.1 --scan   # 扫地址区找有数据的段
```

### 3.3 端到端（启动应用）

1. 建设备：`protocol=modbus-tcp`、`host=192.168.10.1`、`port=502`、`unitId=1`，
   点表填 `40000 / 40001 / 40020 / 40021`（`functionCode=3`、`dataType=u16`）
2. `POST /api/devices/reload` 让采集调度接手
3. 等 1–2 个采集周期
4. **`GET /api/devices/{code}`** 读快照（见 §5 的「为什么不用 WebSocket」）
5. 写回测试：`POST /api/devices/{code}/write`，并**独立回读**确认

## 4. 写回测试：返回 ok ≠ 写进去了

写 `reg40001 = 777`，接口返回：

```json
{"ok":true,"pointKey":"reg40001","value":777,"message":"已下发"}
```

但**独立回读仍是 5632**。

⇒ 原因不是 bug，是 **Modbus 的固有性质**：**PLC 程序的写入优先级高于上位机写入**，
被程序维护的寄存器，我们的写值会被立刻覆盖。

⚠️ **两条要记住的**：

1. **「写成功」的判据不能只有 API 返回 `ok:true`**，必须**独立回读**，
   而且要考虑「上位机写入可能被 PLC 覆盖」这一情形。
2. **不要在真机上随手写寄存器** —— 那是有副作用的操作。
   这次侥幸没出事，是因为目标寄存器（40001）本来就被程序覆盖着。
   **要验写回，先问清楚哪个寄存器是「安全的」（不被 PLC 程序写）。**

## 5. 三个把验证带偏的坑（都不是产品问题）

### 5.1 本机代理挡在回环前面

本机设了 `http_proxy=http://127.0.0.1:60917` ⇒ urllib / curl 访问 `127.0.0.1`
也会走代理 ⇒ 拿到 **502「upstream connect failed」**。

**看起来像应用挂了，其实是代理挡的。** 判据：502 的响应体是代理的口吻，不是应用的口吻。

⇒ 本地回环必须绕过代理：`no_proxy=127.0.0.1,localhost` + `ProxyHandler({})`。

### 5.2 验证脚本退出时把被测进程杀了

用「起应用 + `trap cleanup` 杀进程」的脚本方式让应用常驻 ⇒ **脚本一退出，trap 就把应用杀了**，
下一个验证脚本自然连不上 ⇒ 表现成「应用莫名其妙挂了」。

⇒ 长驻进程用后台任务起，不要挂在一个会退出的脚本的 trap 上。

### 5.3 「没有推送」≠「没采到」

`DeviceCollector.pushValues` **只推「值变化了的」点位**（`!v.sameAs(prev)`）。

⇒ **恒定值的设备只会推第一次** ⇒ 用 WebSocket 监听会**误判成「没采到数据」**。

⇒ 正确判据是 **`GET /api/devices/{code}`**（`DeviceController.toView` 从 `store.latest` 取快照）。

⇒ **判「有没有采到」和判「有没有推送」是两件事**，先分清是哪个。

## 6. 这个验证覆盖什么 / 覆盖不到什么

### 覆盖到了

- Modbus TCP 驱动在 Spring Boot 4.1.2 下能建连、批量读、多功能码
- 点位值转换（`u16` → double）、质量标记（`GOOD`）
- 采集调度接入真实设备（`已连接` → 周期采集）
- 只读点位的写入被正确拒绝（403 + 明确原因）
- 端口口径变更后 Modbus 路径不受影响（端口显式填 502 时行为不变）

### 覆盖不到

- **PLC 程序写入寄存器的竞争行为**（见 §4）—— 没找到「安全的」寄存器做写入验证
- 断线重连、离线判定（`offlineAfterFails`）在真机上的行为
- 多客户端同时连接（S7-200 SMART 不支持，见 §2.1）
- 长时间运行的稳定性（本次只跑了几分钟）
- 485 串口路径（`modbus-rtu` / `modbus-rtu-tcp`）—— 本次没接 485 设备
- 点表里配 `writable=true` 时的写入全链路（写成功但被覆盖，无法区分）

⇒ **本验证覆盖的是「框架升级有没有把这条链路弄坏」，不是「现场配得对不对」。**
后者只能靠真机 —— 而真机也只能验到这里。

## 8. 后续建议

1. **写进交付手册**：S7-200 SMART 的 Modbus TCP 只允许 1 个客户端 ——
   客户接第二套上位机时会报「连接被重置」，看着像设备故障。
