# 验证证据（docs/evidence/）

这里放**「某次验证到底证明了什么」的记录**：升级兼容性、真机实测、性能基线。

## 为什么单独一个目录

**结论会过期，过程不会。**

三个月后再看一份「结论是 OPC UA 可用」的文档，价值不大；
但一份「**当初怀疑哪三个点、怎么查的、哪条结论被推翻过、错因是什么**」的记录，
能让下一个人照着再做一遍 —— 这才是升级 Boot 5 时真正需要的东西。

⇒ 所以这类文档的**重点不是结论，是「结论是怎么来的、怎么被推翻的」**。

## 每篇必须有的三节

| 节 | 要求 | 为什么 |
|---|---|---|
| **复现步骤** | 环境版本（精确到小版本）+ 完整命令 + **真实输出** | 命令能复制、输出能对照。写「跑测试通过」等于没写 |
| **覆盖范围** | 明确列出「**覆盖不到什么**」 | 否则后来人会把「验过了」当成「现场没问题」——**这个误解的代价最大** |
| **修订记录** | 初版结论错在哪、错因、怎么发现的 | 「工具报『没有』时先怀疑工具」这类教训，只写一次就够 |
| 变异验证记录 | 注入什么错误 → 必须红 → 还原 → 必须绿 | 证明「用例不是假绿」。只写「跑一下 exit 0」不能证明任何事 |

## 写作纪律

- **命令与输出必须真跑出来的**，不要为了好看修饰、不要把「应该」写成「已验证」
- **数字要重新核一遍**（有实例：初稿写「1888 个文件」，重新核是 2651 个 —— 更正本身就是要记录的）
- **「看似显然的做法其实不行」的条目要留**，那是信息量最高的部分
  （例：「用 `localhost` vs `127.0.0.1` 造端点错位」——行不通，只有路径部分才会错位）
- 写清**哪些是产品问题、哪些是验证工具的问题**——混在一起后来人没法定位
