## 一、跑起来

### 方式 A：Docker 一键部署（推荐，服务器只需装 Docker）

```bash
git clone https://github.com/ZhuangRenyang/KnowFab-SIRP.git
cd KnowFab-SIRP
sudo bash deploy.sh        # 国内服务器：sudo bash deploy-cn.sh
```

就这三行。deploy.sh 做四件事：生成 .env（随机数据库密码）→ 拉镜像（拉不到自动本地构建）→
**MySQL 在容器里自动建库**（数据存卷，无需任何数据库配置）→ 等健康后打印访问地址和管理员初始密码。
数据在 docker volume 里，重启/崩溃自动拉起；备份用 `docker compose exec mysql mysqldump ...`（见 10.7）。

国内服务器用 `deploy-cn.sh`：不走 GHCR 拉取，直接本地构建，Maven 依赖走阿里云仓。

### 方式 B：源码/裸机运行（本机开发或不用 Docker 的现场）

**前置：MySQL 8**（H2 已于 2026-10-27 废弃——项目要并 ERP，长期数据和备份都要求真数据库）：

```sql
CREATE DATABASE devicehub DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci;
CREATE USER 'devicehub'@'localhost' IDENTIFIED BY '你的密码';
GRANT ALL PRIVILEGES ON devicehub.* TO 'devicehub'@'localhost';
```

连接配置三选一（优先级从高到低）：

1. `install.sh` 生成的 `application.yml`（现场标准路径，数据库密码直接在里面）
2. 环境变量传密码，用包内默认配置（127.0.0.1:3306/devicehub）：

```bash
export DEVICEHUB_DB_PASSWORD='你的密码'

# 有 Maven 的话
mvn spring-boot:run
# 或者用 IDE：直接运行 DeviceHubApplication
```

打开 **http://localhost:8080/app/** —— 新版界面（Vue 3），六个页签全部在内；
旧版跳转壳（`/`、`/login.html`、`/index.html`）已于 2026-10-29 删除，路径由后端转发到 `/app/` SPA 壳：未登录访问自动送到 `/app/#/login`，已登录直接进主界面，旧书签继续有效。`/discover.html` 保留为设备发现的正式书签入口。
车间大屏 `screen.html` / `fault.html` 保持原生零依赖，地址不变。

打包成单文件 jar（部署到客户工控机用这个）：

```bash
mvn clean package
DEVICEHUB_DB_PASSWORD='你的密码' java -jar target/device-hub.jar
```

日志在 `./logs/`，业务数据全在 MySQL 里（备份用 `mysqldump`，见 10.7）。

## 二、这套骨架为什么这样设计

### 只固化三个抽象

**1. 三层设备模型**
`设备类型(点表模板) → 设备实例 → 采集线程`
接新设备 = 填一份点表 JSON，不改代码。

**2. 驱动接口（ProtocolDriver）**
```
connect / read / write / disconnect
```
每个协议一个实现，启动时自动注册进 `DriverRegistry`。
加新协议 = 新建一个类 + 加个 `@Component`，业务层不用动。

**3. 统一数据结构（PointValue）**
不管数据从 Modbus、OPC UA 还是单片机来，出来都是：
```
{ deviceCode, pointKey, name, value, unit, quality, role, ts }
```
存库、推送、告警、对外 API 全都只认它。**这层守住，上层永远不用改。**

### 采集与展示彻底隔离

- 每台设备一个独立线程（`collect-{code}`），独立超时
- 一台掉线不影响其他设备，也不影响网页
- 读写共用一把锁（RTU 是半双工，撞一起必出乱码）
- 只推送变化的值，前端不会被刷屏

### 规模：一个厂几百台，单实例够用

管理整个厂的设备，就是「设备表里有多少条，就采多少台」。加一台是填一条记录，不需要改代码、不需要重启。

**实测数据**（本机，模拟驱动，每台 5 个点、1 秒周期）：

| 设备数 | 内存 | 线程 | CPU（单核） | 全量列表接口 |
|---|---|---|---|---|
| 209 台 | 297 MB | 263 | 4.7% | 60 ms |
| 509 台 | 500 MB | 560 | 10.4% | 40 ms |

线性外推：1000 台约 1 GB 内存、20% 单核。瓶颈不在 Java，在下面这几条物理限制。

**加设备是增量的**：新增只启动新的一台，改配置只重启那一台，删除只停那一台。
509 台在跑时加一台，实测耗时 **83 ms**，其余 508 台连接一次都没断过。

> 早期版本是 `stopAll()` 再全部重启，加一台会让全场设备断一次、加 200 台要 79 秒。已改成增量同步，
> 同样的 200 台现在 25 秒，且不影响已有设备。

### 真正决定「能接多少台」的不是软件，是物理连接

| 接入方式 | 单条链路容量 | 说明 |
|---|---|---|
| Modbus TCP（网口） | 几百台没问题 | 每台一个独立 socket，互不影响。交换机端口够就行 |
| RS485 一条总线 | 标准 32 个从站，**实际 8~16 个稳** | 总线上设备越多，一轮轮询越慢；线长、干扰都会掉包 |
| 串口数量 | 工控机一般 2~4 个 | 不够就加 PCIe 串口卡（4/8/16 口），或换串口服务器（MOXA/宇泰，一个转 8 路） |
| 单片机 / 工控机 | 无上限 | 设备自己往外推 HTTP，不走轮询 |

**采集周期和台数是乘法关系**：一条 485 总线挂 16 台，每台读一次 80 ms，一轮就是 1.3 秒。
所以老设备走 485 的，周期别设 200 ms，设 1~2 秒，把「状态」采到就行。

几十台以上、又都要 1 秒内刷新的，走网口或分多条 485 总线，别全塞一个串口。

### 前端也做了容量处理

500 台设备时 WebSocket 实测 **293 条消息/秒**。如果每条消息都重绘整个页面，浏览器直接卡死。
现在的处理：

- 推送只更新内存，**250 ms 合并渲染一次**
- 卡片 DOM **不重建**，只改数值文本节点
- **分页**（24/48/96/200 可选）+ 搜索 + 状态筛选

所以 500 台和 5 台，页面手感是一样的。

## 三、接一台真设备（以 Modbus 为例）

### 0. 懒人路径：设备发现（不用求厂家）

**入口：后台右上角「发现」按钮**（仅管理员，`/app/#/discovery`）；书签/手册旧链接 `/discover.html` 仍然有效（跳转壳自动送往发现页）。
给接第一台真机的人用的侦察工具，厂家联系不上也能走完：

1. **扫网段**：填 `192.168.1`，多段用英文逗号隔开（`192.168.1,192.168.2,…`），
   并发测谁开着 Modbus 口；单次上限 1024 台，千台工厂一次就能扫完，更多分几批
2. **读寄存器对拍**：对找到的 IP 读 0-100 号寄存器，开着 2 秒自动刷新去设备边
   启停机器——跟着状态走的 0/1/2 就是运行状态点，单调递增的是产量计数，
   报警时非 0 的是报警字（页面上变化的行自动标黄）
3. **生成点表 JSON**：一键生成能直接贴进「新增设备」点表框的 JSON，
   把 name 改成人话、role 改成 status/count/alarm 即可

三条安全边界（刻意设计）：

- **工具只读不写**：只实现功能码 03/04，写功能码（06/16）在接口层就被拒——
  写错一个保持寄存器可能改掉设备加工参数
- **仅管理员可用**：`/api/discovery/**` 后端强制 ADMIN，这本质是台网络扫描器
- **限量**：一次最多扫 1024 台、单帧最多 125 个寄存器、超时上限 5 秒

千台规模两个前提：

- **网络可达**：大厂机器网络通常按车间分 VLAN，服务器必须能路由到那些网段
  （跨 VLAN 扫描要先找网管开通由），扫描器再快也扫不到路由不通的段
- **扫描是一次性的**，真正长期扛 1000 台的是采集侧：500 台压测过，
  1000 台建议轮询周期放宽到 2-5 秒、数据库切 MySQL/PG（系统已支持，改配置即切）、
  按车间分批接入；历史曲线归档见 ROADMAP DH-18

没有硬件想试流程：`python tools/modbus-tcp-sim.py 1502` 起一个本地模拟从站，
0 号寄存器每秒变、3 号每 5 秒 +1，专门用来练"对拍找点"。

**B 路径（串口服务器）同样能扫**：探测和扫描都支持 RTU 透传帧（帧格式下拉选
「RTU 透传」）；新增「**扫从站**」——一台盒子后面挂多台 485 设备各占一个从站号，
点一下扫出哪些从站号活着（并发 8 路、1-247 可调），点从站号直接对拍。
用 TCP 帧去探盒子会超时，报错会直接提示你切 RTU 帧。
模拟器：`python tools/modbus-rtu-tcp-sim.py 1503`（模拟盒子后面挂 1、3 号两台从站）。

边界：本地 485 直连服务器 COM 口的设备暂不支持探测（采集支持，点表先按手册配，
对拍能力在路线图 DH-33）。

### 路径 C：老设备（没有 PLC，只有继电器）怎么接

老设备没有控制器，不代表接不了——**继电器本身就是信号源**。核心思路：
别去读"数据"，去取"开关量"。三招按成本排：

| 招 | 取什么 | 成本 | 得到 |
|---|---|---|---|
| 1. 辅助触点 / 行程开关 | 主接触器或中间继电器的空闲辅助触点（无源干接点）；老机器普遍自带行程/限位开关，直接并联一组 | 0 元 | 运行状态（最准） |
| 2. 接近开关 / 光电开关 | 在动作部位（滑块、模具、出料口）装一个接近/光电开关，每个动作周期感应一次 | 30-80 元 | 产量计数脉冲 |
| 3. 电流互感器（CT） | 卡在主电机电源线上感应电流有无，经变送器输出 RS485 | 50-150 元 | 运行状态，**完全不动控制柜** |

信号进系统的链路：**继电器触点/传感器 → DI 采集模块（Modbus 485，4DI 起步，
一两百块，如金鸽 S275、迅饶 X2）→ 485 转网口盒子 → 系统**。
DI 模块是标准 Modbus，地址表公开——**路径 B 的全套流程直接适用**：
扫描盒子 → 扫从站 → 对拍 → 生成点表（协议选 modbus-rtu-tcp）。
DI 通道是离散输入（功能码 02），发现页探测已支持：功能码选「02 离散输入（DI 通道）」，
生成的点表自动是 bool 类型；通道状态翻转一次就看得到（对拍法照用）。

计数的两个方案，**节拍决定选哪个**：

| 节拍 | 方案 | 原理 |
|---|---|---|
| 慢（≥3 秒/件） | DI 通断 + 系统轮询差分 | 系统每秒读通道状态，"通→断"记一件；点表 role=count、bool |
| 快（<3 秒/件） | 必须选**带计数器寄存器的 DI 模块** | 模块硬件累计脉冲，点表读 32 位计数寄存器 role=count、u32——轮询永远追不上快脉冲 |

报警信号：老机器控制回路里常有"故障继电器"（接报警灯/蜂鸣器的那个），
取它的空闲触点接一个 DI 通道，点表 role=alarm——大屏维修看板立刻能用。

三条安全红线（烧模块是小事，短路是事故）：

1. 只取**无源干接点**（触点本身不带电），不许把 DI 通道并进 220V/380V 主回路
2. 必须从主回路取时，加一个**中间继电器**（几块钱）做电气隔离，DI 只碰中间继电器的触点
3. DI 模块的 COM 公共端接法看模块手册（共阳/共阴），接反就是全部通道读反

添加设备：协议 `modbus-rtu-tcp` + 盒子 IP + DI 模块从站号；
点表用「三色灯干接点」或「DI 计数（老设备）」模板改地址。

### 1. 先确认能通讯

用 **Modbus Poll / Modbus Slave / 组态王** 先读到数，再动代码。
连不上就是接线、站号、波特率、校验位的问题，不是代码问题。

### 2. 加设备

**方式一：网页上点「+ 新增设备」**（推荐，给车间主任用）
填编码、名称、IP、周期，点表从模板选一个改改，保存即生效，不用重启。

**方式二：调接口批量导入**（一次性接几十台时用）

```bash
curl -X POST http://localhost:8080/api/devices \
  -H "Content-Type: application/json" \
  -d '{
    "code": "CNC-02",
    "name": "二号加工中心",
    "location": "一车间 A 区",
    "protocol": "modbus-tcp",
    "host": "192.168.1.50",
    "port": 502,
    "unitId": 1,
    "pollIntervalMs": 1000,
    "enabled": true,
    "apiKey": "key-cnc-02",
    "points": [
      {"key":"status","name":"运行状态","address":0,"functionCode":3,"dataType":"u16","role":"status"},
      {"key":"speed","name":"主轴转速","address":1,"functionCode":3,"dataType":"u16","unit":"rpm"},
      {"key":"output","name":"累计产量","address":4,"functionCode":3,"dataType":"u32","unit":"件","role":"count"},
      {"key":"temperature","name":"主轴温度","address":2,"functionCode":3,"dataType":"s16","unit":"℃","scale":0.1,"decimals":1}
    ]
  }'
```

然后 `POST /api/devices/reload` 让采集生效，不用重启服务。

### 3. 点表字段说明

| 字段 | 说明 |
|---|---|
| `address` | 寄存器地址，**Modbus 从 0 开始**（厂家手册上常写 40001，对应地址 0） |
| `functionCode` | 1=线圈 2=离散输入 3=保持寄存器 4=输入寄存器 |
| `dataType` | u16 / s16 / u32 / s32 / f32 / bool |
| `scale` / `offset` | 实际值 = 原始值 × scale + offset，用于 0.1℃ 这类缩放 |
| `decimals` | 保留几位小数 |
| `role` | 见下表，决定前端和统计怎么处理这个点 |

`role` 一共六种，选错了不会报错，但功能会不对：

| role | 用在什么点 | 系统拿它干什么 |
|---|---|---|
| `status` | 设备状态机寄存器 | 卡片上的运行 / 停机 / 待机 / 报警徽章、顶部统计 |
| `count` | 累计产量、模次、冲次 | 只显示，不参与电费 |
| `energy` | **电表的累计电量寄存器** | 前后相减算用电量、算电费。配到瞬时功率上会算不出来 |
| `power` | 瞬时有功功率 | 只用来显示「当前总负荷」，单位必须是 kW |
| `alarm` | 报警标志位 | 报警计数 |
| `value` | 温度、转速、电流这类普通数值 | 只显示 + 趋势曲线 |

**注意 u32 要占 2 个寄存器**，后面的点地址要相应跳过。

### 4. RS485 / Modbus RTU

```json
{
  "protocol": "modbus-rtu",
  "serialPort": "COM3",
  "baudRate": 9600,
  "dataBits": 8,
  "stopBits": 1,
  "parity": 0,
  "unitId": 1
}
```

现场接线要点（这是你电工底子的优势，纯软件公司做不了）：
- USB 转 485 转换器，A 接 A、B 接 B，**接反了完全没反应**
- 总线末端加 120Ω 终端电阻
- 屏蔽层单端接地，别两端都接
- 站号不能重复，波特率和校验位必须和 PLC 一致
- 变频器旁边走线要远离动力线，否则丢包

### 5. 串口服务器（modbus-rtu-tcp）

工控机不想放车间、或者要用一条网线带多路 485 时，中间加一台串口服务器。

它有三种用法，平台这边的配法不一样：

| 串口服务器模式 | 平台里配什么 | 说明 |
|---|---|---|
| **Modbus 网关**（RTU→TCP） | `protocol: modbus-tcp` | 最推荐，转换由串口服务器做，平台零负担 |
| **TCP 透传 / TCP Server** | `protocol: modbus-rtu-tcp` | 帧原样透传，平台自己算 CRC。老设备只支持这种时用它 |
| Real COM 虚拟串口 | `protocol: modbus-rtu` + `COM5` | 能用，但虚拟串口偶尔卡死，不推荐 |

```json
{
  "code": "CNC-09",
  "name": "经串口服务器接入的老机床",
  "protocol": "modbus-rtu-tcp",
  "host": "192.168.1.200",
  "port": 4001,
  "unitId": 3,
  "pollIntervalMs": 1000,
  "points": [ "…点表和其他协议完全一样…" ]
}
```

**注意 `unitId` 填的是串口服务器后面那台设备的 485 站号，不是串口服务器的地址。**
同一台串口服务器的 4 个口接 4 条总线，每条总线上的站号可以重复，靠 `port` 区分。

#### 这个协议的三个坑（驱动里都已经处理）

1. **RTU 帧没有长度字段，TCP 又没有帧边界。** 只能按功能码推算响应该有多长：
   读位/读寄存器看 `byteCount`，写单个固定 8 字节，异常响应固定 5 字节。
2. **迟到的响应会污染下一次读取。** 上一次超时后，从站的响应可能这时候才到，
   混进下一次读取就整条错位。驱动做了三层防御：
   发请求前清空残留 → 校验单元号和功能码 → 对不上就重发一次（最多一次，避免死循环）。
3. **必须校验 CRC。** TCP 自己有校验，但错位帧的 CRC 一定对不上，这是最后一道防线。

#### 没有硬件时怎么测

带了个模拟从站，不需要任何硬件：

```bash
node tools/rtu-tcp-sim.js 15020
```

然后建一台设备：`protocol=modbus-rtu-tcp`、`host=127.0.0.1`、`port=15020`、`unitId=1`，
点表按下表配：

| 点 | 地址 | 类型 | scale | 预期值 |
|---|---|---|---|---|
| status | 0 | u16 | 1 | 2（运行） |
| speed | 1 | u16 | 1 | 1450 |
| output | 2 | u32 | 1 | 12345（**占 2 个寄存器**） |
| current | 4 | u16 | 0.01 | 12.5 A |
| temperature | 5 | s16 | 0.1 | 38.5 ℃ |

能读到上面这组值，说明驱动、点表、缩放全都对。写入也支持，模拟器会记住写入的值。

## 四、接口清单

### 内部（给管理后台用，无鉴权，别暴露到公网）

| 方法 | 路径 | 说明 |
|---|---|---|

## 五、加一个新协议（OPC UA / 三菱 MC / 单片机私有协议）

三步，业务代码一行不用改：

```java
public class MyPlcDriver extends AbstractModbusDriver {   // 或直接 implements ProtocolDriver
    @Override public String type() { return "my-plc"; }
    @Override public void connect(DriverContext ctx) { ... }
    @Override protected byte[] request(DriverContext ctx, int fc, int addr, int arg) { ... }
    @Override public void disconnect() { ... }

    @Component
    public static class Factory implements DriverFactory {
        public String type() { return "my-plc"; }
        public ProtocolDriver create() { return new MyPlcDriver(); }
    }
}
```

然后设备的 `protocol` 填 `my-plc` 就行。

**想看真实范本**：`ModbusRtuOverTcpDriver` 就是照这个写的，而且它比 Modbus TCP 复杂得多
（要自己算 CRC、自己推算响应长度），照着它改基本不会踩坑。

**单片机 / 工控机** 这一类最省事：不用走 Modbus，直接在设备上跑一个几十行的程序，定时 `POST` 到
`/api/devices/{code}/push`（这个接口还没写，需要时自己加一个 Controller，
它只需要把收到的 Map 塞进 `SnapshotStore` 和 `WsHandler`）。

## 六、为什么没有授权锁（2026-10-27 移除）

原来这一节讲的是 RSA 授权：签名 + 机器码 + 到期日 + 设备数上限 + 功能位。现在整块删掉了。

### 为什么删

不是因为做不出来，是**收益抵不上麻烦**：

| 代价 | 具体表现 |
|---|---|
| 售后成本 | 客户换服务器、重装系统、加内存导致机器码变化 → 授权失效 → 半夜打电话。这类工单占比很高，且全是"业务没坏但系统不能用" |
| 交付摩擦 | 每次交付要签一份授权、算到期日、填设备数；客户扩产 5 台要重新签一次 |
| 绕过成本太低 | 改 jar 里一个方法就能破。防的是老实人，防不住想省钱的人 |
| 现金流没变好 | 真正约束回款的是合同和尾款，不是客户端的一行校验 |

一个 3~20 万的定制项目，客户想赖账的办法多得很，授权锁只增加你自己的工作量。

### 现在靠什么保护

| 手段 | 防的是什么 |
|---|---|
| 升级包 RSA 验签 | 内网有人替换 jar / 传恶意包。**这条保留了**，因为它是防投毒，不是防客户 |
| 设备 API Key（每台独立、可重置可停用） | 客户把对外接口转卖给第三方 |
| 登录 + 三级角色 | 车间里谁都能删设备、改电价 |
| 操作审计（待做，ROADMAP DH-24） | 出了事查不到是谁改的 |

### 代码里删了什么

`com.factory.hub.license` 整个包（9 个类）、`LicenseService` 在采集/告警/设备/对外接口里的 4 处闸门、
页面上的授权胶囊和授权弹窗、`application.yml` 里的 `license:` 段、`tools/LicenseKeygen.java`。

**升级包验签的公钥保留**，配置键从 `license.public-key` 改成 `system.update.public-key`
（老键名仍兼容）。私钥 `tools/keys/private.key` 只用于签升级包，`PackUpdate` 需要它。

### 如果哪天想加回来

先想清楚上面那张代价表。真要做，别做客户端授权，做**服务端许可**：
核心数据同步到你的服务器，断网 30 天后功能降级。那个绕不过去，也省得跟客户解释机器码。

## 七、能耗与电费（最容易卖出价钱的一层）

### 为什么加这个

你跟老板说「我能看到每台机器在跑」，他觉得这是个技术活，会压价。
你说「3 号注塑机这个月吃掉 4200 度电、按峰谷电价 3100 块、比 2 号机高 38%」，
他会立刻坐直——这个数他自己也想算，但没人能算到单台机器。

同一套采集底座，多一个电价维度，报价能往上走一档。
而且客户第二年还会找你，因为电费每个月都在涨。

### 怎么配（不改代码，只改点表）

在设备点表里加两项：

| key | name | role | unit | dataType | 说明 |
|---|---|---|---|---|---|
| `energy` | 累计电量 | **energy** | kWh | u32 | 电表的累计电量寄存器 |
| `power` | 有功功率 | **power** | kW | u16 / u32 | 瞬时功率，只用来显示当前负荷 |

`role` 必须是 `energy`，系统靠它认出「这是一个只增不减的累计量」。
配错的后果见下面「三个坑」。

现场三种接入方式，按代价从低到高：

1. **柜里加一块多功能电表**（最推荐）——不动机器，只在电控柜进线处装一块
   带 485 的电表，读电压 / 电流 / 功率 / 电量。几百块成本、半小时装完。
   要单独算每台机器的电量，就把表装在这台机器的断路器下面。
2. **PLC 里本来就有电量寄存器**——很多变频器、伺服驱动器自己统计 kWh，
   直接读它的寄存器，零成本。
3. **用电流互感器自己算**——只有电流没有电量时，按 `P = √3·U·I·cosφ` 估算。
   不建议：功率因数一直在变，估出来跟电表差 5~15%，客户一对账就露馅。

### 数据是怎么变成钱的

```
累计电量（12345.67 kWh，只增不减）
   │  每秒扫一次快照，跟上次读数相减
   ▼
本次增量（0.0025 kWh）
   │  看这个时刻属于哪个电价时段
   ▼
按「小时 × 时段」累加进内存桶
   │  整点结算 + 每 10 分钟落库
   ▼
energy_hourly 表：device_code + hour_start + seg_type + kwh + price + cost
   │  查询时聚合
   ▼
今日电费 / 本月电费 / 峰谷分布 / 设备排行
```

关键设计：**当前这一小时的数据只在内存里，不在库里。**
统计任务每 10 分钟才落一次库，但客户点开页面必须看到「到现在为止」的数。
所以查询一律是「数据库里 `[今天0点, 当前整点)` + 内存里当前这一小时」，
**上界不含当前整点**，这样才不会把同一批电量算两遍。

### 三个坑（都已经处理了，但你得知道为什么）

**1. 读数变小 = 换表或清零。**
`delta = cur - prev` 这样写，遇到换表就得到负数，把整天的电量冲掉，
客户看到「今天用了 -800 度」。这里的处理是：读数变小就记 0，等下一个周期。
代价是丢掉清零那一瞬间的几度电，换来永远不会算出一个离谱的大数。

有人会用数据类型位宽去判回绕（u16 最大 6553.5 度就会溢出）。但一个采集周期内
溢出的概率远低于清零，而误判回绕的代价是多算几十万度。要拿去跟客户对账的系统，
这个错不能犯。真遇到 u16 溢出的表，把点表改成 u32。

**2. 断线补偿。**
设备离线两小时再上线，一次读数就跨了两小时的电。这部分是真的用了，必须算，
但归到「上线那一小时」会让这小时电费突然翻几倍。所以这类增量单独记在
`backfill_kwh` 里，设备排行会标「含补偿」，让客户知道不是软件算错了。

**3. 点表配错。**
最常见的错误是把「瞬时功率」错配成 `role=energy`。功率上下跳，读数天天变小。
系统会统计读数变小的次数，超过阈值就提示「这个点可能配成了瞬时功率」。
比让客户盯着一个不动的电费数字猜要强得多。

### 电价怎么配

点「能耗分析 → 电价设置」，网页上直接改，保存立即生效，不用重启服务。
默认方案是示例值（低谷 0.35 / 平段 0.68 / 高峰 1.05 / 尖峰 1.32 元/度），
**交付时必须按客户当地供电局的《分时电价执行细则》改**——各省差异很大，
有的地方还分深谷、季节性尖峰。

保存时会做体检：

- 时段有没有覆盖满 24 小时（漏掉的部分进「未计价」，只记度数不算钱）
- 有没有时段互相重叠（重叠时取第一个匹配到的）

有问题不阻止保存——客户可能确实有特殊政策——但会把警告显示在页面上。
不提示的话，电费算少了客户会以为是软件错了。

**单价是写进每一行记录里的快照。** 以后改电价，历史账单不会跟着变。
这点对账很重要，别改成查询时现算。

### 接口

| 接口 | 用途 |
|---|---|
| `GET /api/energy/overview?days=7` | 今日/本月电量电费、峰谷分布、日趋势、当前负荷 |
| `GET /api/energy/devices?range=today\|7d\|month` | 设备能耗排行 |
| `GET /api/energy/device/{code}?date=YYYY-MM-DD` | 单设备 24 小时明细 |
| `GET /api/energy/tariff` | 读电价方案 + 体检结果 |
| `POST /api/energy/tariff` | 保存电价，立即生效 |
| `POST /api/energy/purge` | 清空全部能耗历史（要 `{"confirm":true}`） |

这些都是管理端接口。客户要拿电费数据对接 MES / ERP 时，在 `OpenApiController`
里另开一个带 API Key 校验的端点，别把这几个直接暴露出去。

### 数据量

一台设备一小时最多 4 行（四个时段），一年 8760 行，500 台约 438 万行/年。
MySQL 带得动；超过 2000 台把历史查询走归档表（ROADMAP DH-18），或把汇总数据
单独迁到 TDengine。系统会自动删除 400 天以前的数据，不用你管。

### 演示数据（交付前必须关）

首次启动会生成 7 天假能耗数据，这样打开页面就能看到完整的趋势图和峰谷分布，
而不是一片空白——能耗功能是靠时间积累出价值的，刚装上就是一堆 0，
客户看不出这东西有什么用。

**正式交付前必须关掉**，否则客户看到的是假电费：

```yaml
energy:
  demo-seed: false
```

然后调一次 `POST /api/energy/purge`（body 带 `{"confirm": true}`）清掉假数据。

## 八、报表（班次产量 / 稼动率 / 停机原因 / Excel 导出）

这一节说清楚三件事：报表的数字怎么来的、为什么这么算、客户会怎么挑刺。

### 数据从哪来：一张小时表算到底

`prod_hourly` 表，粒度「一台设备 × 一个小时」，存四类状态的秒数和这一小时的产量。

```
device_code | hour_start | run_sec | idle_sec | stop_sec | alarm_sec | unknown_sec | output | backfill
```

为什么按小时存、不直接存班次：

- 客户改班次是常事（三班倒改两班倒、夜班从 20 点挪到 21 点）。按小时存，
  改完班次历史报表还能重算；按班次存，改一次等于把历史数据全废掉。
- 一天一台设备 24 行，500 台也就 1.2 万行，查询毫无压力。

数据量：一台一年 8760 行，500 台约 438 万行/年，和能耗表同量级。超 2000 台走历史归档（DH-18）或迁时序库。

### 秒数怎么算（这里错一次，客户就不信你了）

不能「采一次记一秒」——丢一次采样就少记一秒，一天能差几个小时。正确做法是用时间差：

1. 拿这一笔采样和上一笔的 `ts` 求差，这几十秒/几秒归给**上一笔的状态**（状态是在这一笔才变的）。
2. 间隔超过 15 秒（`MAX_GAP_MS`）一律不记。设备离线两小时再上线，
   差值 7200 秒直接记进某一小时，会把那一小时填满 2 倍。这段空白留在 `unknown_sec`，
   报表上能看出数据不连续——这比假装数据完整重要。
3. 产量用累计计数器算增量：`delta = 当前 - 上次`。**读数变小一律记 0**（换班清零、换表清零），
   绝不能记负数，否则客户看到「今天产了 -800 件」。
4. 断线重连后一次性补记的产量，标 `backfill`，让客户知道那小时为什么突然高一截。

### 班次归属：夜班算开班那天

26 日夜班 20:00 → 27 日 08:00，产量算 **26 日**。车间就是这么记账的：
晚上八点开班，第二天早上八点交班，这一班记在开班那天。

所以「26 日的报表」会包含 27 日凌晨 0-8 点的数据——这是对的，不是 bug。
跨零点班次在 `ShiftPlan.windowOf()` 里处理，前端和导出都用同一套窗口，不会两处算出两个数。

班次之间不能重叠。重叠会让同一小时进两个班，产量凭空翻倍——
这种错客户自己发现不了，所以保存时直接拒绝（`POST /api/reports/shifts` 返回 `ok:false`）。

### 指标定义（跟客户对齐，别自己发明）

| 指标 | 算法 | 说明 |
|---|---|---|
| 产量 | 计数器增量之和 | 只统计 `role=count` 的点位 |
| 稼动率 | 运行时长 ÷ 已记录时长 | **不是** ÷ 24 小时。÷24 会把没排班的夜里也算成损失，客户不认 |
| 停机时长 | `role=status` 值为 0 的时长 | 待机（1）不算停机，否则「等料」和「坏了」混在一起 |
| 停机次数/原因 | 停机类告警事件 | 规则名就是原因分类，想细分就在报警规则里多建几条 |
| 数据完整度 | 已记录秒数 ÷ 应有秒数 | 低于 80% 打印在 Excel 里，提醒这天的数别直接拿去报 |

**没做 OEE**：OEE = 可用率 × 性能 × 良品率，良品率得从客户的 MES 或者质检记录来，
采集层拿不到。硬凑一个「理论产量」算出来的 OEE 是假数，比没有更糟。
等客户能提供计划产量和不良数，在 `ProdHourly` 上加两列就能算——这是 v2 的事。

### 页面与接口

页面：`报表` 页签 → 日期切换 / 四个 KPI（产量、稼动率、停机时长、停机次数）/
每小时产量柱状图 / 停机原因排行 / 班次汇总表 / 设备明细表 / 导出 Excel。

```
GET  /api/reports/daily?date=2026-10-26     单日全部数据（一次请求，页面只拉一次）
GET  /api/reports/range?days=7              近 N 天趋势（上限 90）
GET  /api/reports/shifts                    班次方案
POST /api/reports/shifts                    保存班次（重叠直接拒绝）
GET  /api/reports/export?date=2026-10-26    下载 xlsx
POST /api/reports/purge {"confirm":true}    清演示数据
```

导出的 xlsx 三个 sheet：**班次汇总 / 设备明细 / 停机原因**。
表头冻结、列宽固定、数字右对齐，车间主任拿到能直接打印，不用再调半小时格式。
用 POI 而不是 CSV：CSV 在中文 Windows 上双击是乱码，一个「导出来打不开」的印象能把前面所有工作抵消掉。

### 演示数据

`report.demo-seed: true` 会灌 6 天假数据（今天不灌，让真实数据自己跑）。
交付前改 `false`，并调 `POST /api/reports/purge {"confirm":true}`。

坑：假数据只给有 `role=count` 点位的设备造产量。总电表没有产量点，
如果也给它造 1265 件，客户一眼就看出数据是编的，整份报表的可信度就没了。

### 实测（本机 4 台模拟设备）

- 单日报表：产量 2690 件、稼动率 70.1%、三个班次分项合计与总计一致
- 电表产量为 0，稼动率仍统计（没有 count 点不等于没数据）
- 导出 xlsx：3 个 sheet、中文表头、`70.5%` 这类格式化数字正确
- 跨零点班次：中班 16:00-00:00 的产量落在当天，夜班 00:00-08:00 单独一列，不重不漏
- 清演示数据不带 `confirm` 被拒

## 九、基本电费与需量（最容易多收钱、也最容易算错的一块）

电费账单不是只有「用了多少度」：大工业电费 = 电度电费 + **基本电费** + 力调电费。
第七节那套分时电价只管电度电费，这一节管基本电费。

现场常见比例：一个中等机加工厂，电度电费七八千，基本电费一万多。**基本电费比电度还贵**，
但市面上的采集系统基本都不算它——这就是能把这个模块卖出价钱的原因。

### 数据粒度：必须 15 分钟，小时表算不出来

`demand_window` 表，一台表一天 96 行：窗口起点、电量、需量（= 电量 × 4）。

为什么不能复用 `energy_hourly`：一小时内如果前 15 分钟满负荷、后 45 分钟停机，
小时平均只有 1/4，而供电局按那 15 分钟收满额需量。
用小时表算需量，每月少算一大截，客户拿电费单一对就露馅。

同理，窗口必须**对齐整 15 分钟**（:00 :15 :30 :45），不能从服务启动时刻开始切，
否则重启一次切分点全乱，峰值跟电费单永远对不上。

### 三个会让需量算错的坑

1. **断线补偿的电量不能计需量。**设备离线两小时再上线，一次读数带回来 2 小时的电量，
   全塞进当前窗口，算出来是真实负荷的 8 倍。月峰值一旦被这条假数据顶上去，
   客户可能据此去申请扩容，白花钱，而且不知道是软件算错。
   `EnergyRollup` 里 `backfill=true` 的电量直接丢弃（`DemandTracker.feed` 第一行判断）。
2. **一台设备只能配一个 `role=energy` 点。**挂「总表 + 分表」两个电量点，需量会加两遍。
   分表请配到别的设备上，或用设备树区分。
3. **别做「本月预计需量」。**需量取最大值，已出现的峰值不会被后面拉低，
   「预计」等于「当前峰值」，画一条平滑预测线纯属糊弄人。
   客户真正要的是「还剩多少余量」——那是减法。

### 基本电费怎么算：两种都摆出来

| 计费方式 | 算法 | 适合谁 |
|---|---|---|
| 按需量 | 当月最大需量 kW × 需量电价（元/kW·月） | 负荷波动大、常年开不满的厂 |
| 按容量 | 变压器容量 kVA × 容量电价（元/kVA·月） | 三班倒、负荷稳的厂 |

`billingMode: AUTO` 会把两种都算出来取便宜的，页面上同时显示两个数并标出差额——
客户每年申报计费方式时，这个数就是决策依据（实测演示数据：按需量 11,407 元 vs 按容量 18,400 元，差 6,993 元/月）。

### 超需量预警

`DemandMonitor` 每 30 秒算一次当月峰值，按合同需量的 90%（可配）触发：

- **接近**：MAJOR「已到合同需量的 94%，还剩 30 kW 余量」
- **超了**：CRITICAL「已超合同 4%，本月基本电费按 520 kW 计，超容部分有的地区按 2 倍加收」
- 回落到 85% 以下自动解除（留 5% 滞回，防止在阈值附近反复报）

为什么单独一个 Monitor 而不是塞进 `AlarmEngine`：那个引擎的输入是「设备点位采样」，
需量是「时间窗口聚合量」，没有对应点位。硬塞一个虚拟点会让规则配置界面多出客户看不懂的项。
但复用同一套 `AlarmEvent`（报警页能看到）+ `AlarmNotifier`（微信能收到），保持一个报警入口。

### 页面上必须说清楚的一件事

「本月电费 3,641 元」和「本月基本电费 11,407 元」并排放，客户第一反应是「你算错了」。
所以：
- 电度电费那个 KPI 副标题写「仅电度电费」
- 需量面板里给出合计：**本月电费合计 = 电度 3,641.55 + 基本 11,406.99 = 15,048.54 元（力调电费未计）**

力调电费（功率因数调整）要功率因数数据，目前没采，如实写「未计」，不要装作算全了。

## 十、部署到客户服务器（Linux / Ubuntu）与升级

部署形态：**客户机房一台 Linux 服务器（Ubuntu 20.04+/麒麟/CentOS 7+），设备在车间，走网线或 WiFi 连到服务器**。
不是工控机、不是 Docker、不依赖外网。

### 10.1 一键安装

把 `device-hub.jar`、`install.sh`、`bin/` 一起拷到服务器同一个目录，然后：

```bash
sudo ./install.sh                    # 默认 /opt/device-hub，端口 8080
sudo PORT=9000 ./install.sh          # 换端口
sudo ./install.sh --allow-web-restart # 允许网页上点升级直接重启（见 10.3）
```

脚本做四件事，**可以重复执行**（装坏了重跑，不会覆盖 data）：

1. 检查 Java 17+（没有就用系统源装；离线环境把 `jre/` 放同目录，脚本会优先用它）
2. 建系统用户 `devicehub`（nologin，跑服务不跑 shell）、建目录、首次写入 `application.yml`
3. 注册 systemd 服务（`Restart=always`，崩溃 5 秒后自动拉起；日志进 `logs/stdout.log`）
4. 防火墙放行端口 → 启动 → 轮询 `/api/system/version` 自检 → 打印访问地址

装完打开 `http://服务器IP:8080`。报表、需量、早报这些页面都在。

### 10.2 目录结构（交付后现场长这样）

```
/opt/device-hub/
├── device-hub.jar          程序（升级时被替换的就是这个）
├── application.yml         配置（含数据库密码，重装不覆盖）
├── data/                   本地文件（日志附件等）；业务数据在 MySQL，升级绝不动
├── logs/                   stdout.log / stderr.log / update.log
├── updates/                升级包暂存（inbox 上传、staged 待应用、pending.env 登记）
├── migrations/             升级包带来的数据库脚本，启动时自动执行（见 10.13）
├── backups/                每次升级前的 jar 备份，回滚用
└── bin/
    ├── apply-pending.sh    启动前应用升级包
    ├── upgrade.sh          命令行升级/回滚（带健康检查和自动退回）
    └── update-pub.pem      升级包验签公钥
```

### 10.3 升级：为什么不是「点一下热更新」

Linux 上 jar 可以被覆盖（inode 换了，进程跑的还是老代码），但那一瞬间内存里的类和磁盘上的
不一致、数据库结构已经变了——出问题时你根本不知道跑的是哪个版本。所以设计成三段：

1. **网页「系统」页上传包** → 验签 + 逐文件 sha256 校验 → 解压到 `updates/staged/<版本>` → 写 `pending.env`
2. **应用**（两条路，客户环境二选一）
   - 安全模式（默认）：页面提示执行 `sudo systemctl restart device-hub`，由管理员挑时间
   - 一键模式：安装时加 `--allow-web-restart`，页面按钮直接重启（只授了一条 `systemctl restart device-hub` 的 sudo 权限）
3. **重启时** `ExecStartPre=bin/apply-pending.sh` 备份旧 jar → 再校验一次 sha256 → 换文件
   → 把包里的 `migration.sql` 放进 `migrations/` → 起服务
4. **服务起来的第一件事**（任何 Bean 创建之前）执行没跑过的迁移脚本，再交给 Hibernate 建表。
   顺序不能反，原因见 10.13

**起不来自动退回**：用 `bin/upgrade.sh` 升级时有健康检查，40 秒内 `/api/system/version` 不通就自动恢复备份的 jar 再启动。

```bash
sudo bin/upgrade.sh --status                      # 当前版本、待应用、备份列表
sudo bin/upgrade.sh device-hub-1.1.0.zip          # 离线升级（车间没外网就走这条）
sudo bin/upgrade.sh --rollback                    # 回滚到上一个版本
```

### 10.4 升级包怎么打（供应商侧，不进交付包）

```bash
java tools/PackUpdate.java \
     --jar target/device-hub.jar \
     --version 1.1.0 \
     --notes "报表加 Excel 导出；修复需量窗口重启后错位" \
     --migration src/main/resources/db/migration/1.1.0.sql \
     --key tools/keys/private.key \
     --out dist/device-hub-1.1.0.zip
```

`--migration` 是可选的：这个版本改了表结构就带上，没改就别带（不需要动库的版本别塞脚本）。

**想换一对签名密钥**（私钥泄露、或者换个客户一套）：

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.key
openssl rsa -in private.key -pubout -out public.key
# 公钥内容填到 application.yml 的 system.update.public-key（或 --system.update.public-key 启动参数）
```

换完之后**旧包一律验签失败**，已经发出去的升级包全部作废——这是特性不是 bug。

包里有 `manifest.json`（版本、说明、每个文件的 sha256）+ `manifest.sig`（**用私钥签的**）+ jar。

为什么要签名：升级通道是整个系统权限最大的入口，能升级就能换成任何代码。
客户手上只有公钥，内网被人放一个恶意包上来也装不进去。**这不是防客户，是防内网投毒。**

服务端会拒绝这几种包：签名不对、版本不比当前新、`minFrom` 不满足、试图写 `data/`
（客户数据不允许被升级包覆盖）、jar 的 sha256 对不上。

### 10.5 现场通信：网线 / WiFi 连设备

设备侧不走串口，走网络（Modbus TCP / 串口服务器透传），所以每台设备有两个参数必须按现场调：

| 参数 | 默认 | 什么时候要改 |
|---|---|---|
| 超时 `timeoutMs` | 800ms | **走 WiFi / 4G 路由 / 无线网桥就调到 2000~3000**。800ms 是交换机直连的值 |
| 离线阈值 `offlineAfterFails` | 2 次 | 无线不稳可调到 3~5，否则设备会在页面上反复闪红，运行人员很快学会"红色不用管" |

断线重连是**指数退避 + 随机抖动**（1s→2s→4s→8s→16s→30s 封顶，再加 0~30% 抖动）。
为什么要抖动：交换机重启或 AP 掉线时几百台设备同时断、同时重连，固定间隔重连等于把恢复瞬间
变成一次小型 SYN 洪水，结果是"网络已经好了，系统还要几分钟才恢复"。抖动让它们错开，总恢复时间反而更短。

TCP keepalive 已调紧（空闲 60s + 每 10s 探 + 3 次判死，约 90 秒内发现静默断链）。
Linux 默认是 7200 秒——无线网桥掉线、NAT 表老化这类"静默断链"，socket 一直显示已连接，
只有下次读写超时才暴露，采集周期长的设备能瞒你一分钟以上。

### 10.6 其它必须做的事

1. **时间必须对（NTP）**。服务器时间错，历史曲线、班次报表、需量窗口全乱：

   ```bash
   sudo timedatectl set-timezone Asia/Shanghai
   sudo timedatectl set-ntp true
   ```

2. **数据备份**。业务数据全在 MySQL 里，备份就是 `mysqldump`（见 10.7 结尾的 crontab 示例）；
   `data/` 目录只有本地附件类文件，也顺带拷一下不亏：

   ```bash
   # 加到 crontab：每天 2 点备份，留 14 天
   0 2 * * * tar czf /backup/device-hub-$(date +\%F).tgz -C /opt/device-hub data && find /backup -name 'device-hub-*.tgz' -mtime +14 -delete
   ```

3. **关演示数据**。交付前到「系统 → 系统设置」把三个演示数据开关关掉、保存，
   再分别点三个清除按钮——不用改文件、不用调接口（见 10.12）。

### 10.7 数据库：MySQL 8（必装前提，H2 已废弃）

**2026-10-27 起 H2 已废弃，驱动从包里移除**——项目后面要并 ERP 功能，
长期数据、备份、和 ERP 共库都要求真数据库，嵌入库没有前途。
现在只有两种选择：

| 场景 | 选哪个 | 原因 |
|---|---|---|
| 默认 | **MySQL 8**（必装） | ERP 集成、`mysqldump` 备份、DBA 运维体系都是现成的 |
| 客户指定 PG / 要接 BI | **PostgreSQL 14+** | 保留为可选项，代码路径三库一致 |

一键安装时数据库参数**必填**，连不上直接终止（不再有"先装上再说"的兜底）：

```bash
sudo ./install.sh --db-pass '你的密码'                        # 默认连 127.0.0.1:3306/device_hub
sudo ./install.sh --db-pass '你的密码' \
     --db-host 10.0.0.5 --db-port 3306 --db-name device_hub --db-user devicehub
sudo ./install.sh --db pg --db-pass '你的密码' --db-host 10.0.0.5   # PG 可选
```

脚本会先探端口，**连不上就 die** 并给出排查清单；装好后写 `$DIR/application.yml`
（数据源、管理员密码一个文件说清），systemd 直接用它启动。
`--db h2` 会被明确拒绝并提示废弃原因。

手工配置（不走安装脚本时）就是改数据源：

```yaml
spring:
  datasource:
    url: jdbc:mysql://10.0.0.5:3306/device_hub?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true&rewriteBatchedStatements=true
    driver-class-name: com.mysql.cj.jdbc.Driver
    username: devicehub
    password: "***"
```

五个必须注意的点：

1. **建库要 utf8mb4**，否则设备名里的中文/特殊字符会报错：
   `CREATE DATABASE device_hub DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci;`
2. **时区必须对**。MySQL 连接串里 `serverTimezone=Asia/Shanghai`，服务器也要 `timedatectl set-timezone Asia/Shanghai`。
   时区错了，小时报表、班次、需量窗口会整体偏移，比数据错还难查。
3. **MySQL 8 默认 `caching_sha2_password`**，不开 SSL 时必须带 `allowPublicKeyRetrieval=true`，否则连不上报
   "Public Key Retrieval is not allowed"。
4. **长文本列的坑（2026-10-27 已修）**：Hibernate 6 在 MySQL 上把 `@Lob String`
   映射成 `tinytext`（只有 255 字节），导致 `Data too long`。修复方式是长文本字段统一用
   `@JdbcTypeCode(SqlTypes.LONGVARCHAR)`（MySQL→text、PG→text）。
   以后新增长文本字段别再用 `@Lob`。MySQL 严格模式会拦下一切超长写入。
5. **旧版 H2 数据不会自动迁**。老安装升级到本版前先装 MySQL 建库；
   旧数据用 H2 的 `SCRIPT TO 'dump.sql'` 导出，但 SQL 方言要手工改
   （自增主键、`CLOB`、`IDENTITY` 都不一样），量小才值得干，量大部分靠重灌。

备份（MySQL 是唯一路径，装完就该配）。**直接用自带脚本**，凭据自动从 `application.yml` 读取：

```bash
sudo ./bin/backup.sh            # 手工跑一次：backups/库名-时间.sql.gz，默认保留 14 天
sudo ./bin/backup.sh 30         # 保留 30 天
# 每天 02:30 自动备份（加进 crontab）：
#   30 2 * * * /opt/device-hub/bin/backup.sh >> /opt/device-hub/logs/backup.log 2>&1
```

恢复（先停服务或确认低峰）：`gunzip < backups/xxx.sql.gz | mysql -u<user> -p <库名>`。
Docker 部署的用 `docker compose exec mysql mysqldump ...`，volume 记得一并备份。

### 10.10 对外 API Key 管理

「设备监控」选中设备 → 详情里有一行 **API Key**：

- **复制**：给对接方（MES/看板/外包系统）
- **重置**：生成新 key，旧 key 立刻失效——正在对接的系统会断，重置前先通知对方
- **停用 / 启用**：停用只挡 `/open/v1/**`，**采集照常**。客户和某个外包系统不合作了，停 key 就行，不用删设备
- 留空 = 不对外（没 key 的设备，对外接口一律 401）

Key 格式是 `设备码_24位随机`（去掉了容易看错的 l/o/0/1），现场要电话报 key 时报得清楚。

接口调用：

```bash
curl "http://服务器:8080/open/v1/CNC-01/status?key=cnc01_xxxxxxxx"
curl -H "X-Api-Key: cnc01_xxxxxxxx" "http://服务器:8080/open/v1/CNC-01/values"

# 这台机器的报警：MES 最常问"它现在为什么停"
curl "http://服务器:8080/open/v1/CNC-01/alarms?key=cnc01_xxxxxxxx"            # 只看未恢复的（含已确认）
curl "http://服务器:8080/open/v1/CNC-01/alarms?key=cnc01_xxxxxxxx&open=false"  # 最近 100 条历史，含已恢复
# 响应里带 plcWords：伺服/PLC 报警字（按设备配置的品牌翻译成文字含义）
```

> 重置 key 属于写操作，只有管理员和车间主任能调；班组长点了会得到 403。见 10.11。

### 10.11 登录与账号（四级角色）

系统有登录，不登录只能看到一个登录页。四个角色对应厂里的真实岗位：

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **管理员** ADMIN | 全部：设备、报警规则、电价、班次、需量参数、用户、系统升级 | — |
| **车间主任** MANAGER | 设备增删改、报警规则、确认告警、班次设置 | 改电价/需量参数、用户管理、系统升级 |
| **班组长** LEADER | 看板、看历史、确认告警 | 任何配置改动（按钮会隐藏，接口返回 403） |
| **销售** SALES | 只读「销售查询」：现存/订单占用/可承诺量/所在仓库，可导出无成本 Excel | 设备、报警、能耗、报表、ERP 明细与全部写操作（接口 403，菜单里也不出现） |

**初始管理员**：`install.sh` 安装时随机生成 12 位密码，写在 `$DIR/INITIAL_ADMIN.txt`，
安装结束也会打印出来。不是 `admin123` —— 客户现场装上就忘改，等于门一直开着。

手工部署（没走 install.sh）时，`application.yml` 里 `system.admin.password` 留空，
首次启动会随机生成，写进 `data/initial-admin.txt` 并打在日志里。

**改密码**：点右上角用户名 → 输入原密码 + 新密码。管理员也能在「系统 → 用户管理」里给别人重置。

**登录失败限流**：同一 IP 连错 5 次锁 5 分钟（内存计数，重启清零）。
反代后面所有请求都是网关 IP 时会误伤，那种情况应该在网关上做限流。

**两个刻意留的匿名入口**（漏一个就是事故，改安全配置前先读这段）：

1. `/api/system/version` —— `install.sh` / `upgrade.sh` 的健康检查靠它，401 会让安装脚本误判"服务没起来"
2. `/ws/**` —— 实时数据 WebSocket，握手不走登录校验

另外 `/open/**` 走设备 API Key，是给客户 MES 对接的，不能要求登录。

**最后一道保险**：不能停用/降级/删除**最后一个启用的管理员**，接口会直接拒绝并说明原因。
真发生了客户只能改数据库才能救回来，这种事故一次都不该有。

### 10.12 系统设置：哪些能在后台改，哪些不能

客户现场有一条铁律：**能让他们在页面上改的，就别让他们登服务器改文件**。
改 yml 要重启，重启就断采集；而且现场没人记得住 yml 的缩进。

「系统」页 → 系统设置，能改这些：

| 配置项 | 生效方式 | 说明 |
|---|---|---|
| 更新源 | 只读 | 内置固定 Gitee（兜底 GitHub），页面不提供修改 |
| 允许网页上一键重启 | 立即 | 打开前要先确认安装时开过 sudo 规则，否则按钮会失败并提示 |
| 批量告警合并阈值 | 立即 | 默认 8 条；全厂掉线时合并成一条，别刷爆群 |
| 告警历史保留天数 | 立即 | 默认 180 天；只清已恢复的 |
| 能耗 / 报表 / 需量演示数据 | **重启生效** | 只控制"启动时要不要生成"，已有假数据要用下面的清除按钮 |

取值顺序是 **页面覆盖值 → application.yml → 代码兜底**。改回默认值保存时，
对应的覆盖行会被自动删掉（`app_setting` 里只留真正改过的项），
所以"到底哪项被动过"一眼能查。单项也能点「恢复默认」直接退回 yml 的值。

**故意不给页面开关的项**（页面上会列出来并写原因）：

| 项 | 为什么 |
|---|---|
| 服务端口 | 要同步改 systemd 启动参数和防火墙，重装时 `PORT=9000 ./install.sh` |
| 数据库地址 / 密码 | 换库要停服、导数据，在线切会让表结构对不上 |
| 升级暂存目录 | 和 `bin/apply-pending.sh` 约定死了，改了升级静默失效 |
| 采集数据目录 | 客户全部业务数据，只读展示，避免手抖 |

**为什么演示数据要单独给清除按钮**：开关只管"下次启动生成不生成"。
只关开关不清数据，客户看到的还是编出来的电费和产量——这是数据可信度问题，
一旦被发现，整份数据都不作数了。所以清除按钮放在开关下面，清完如果开关还开着会明确提示
"下次重启还会重新生成"。

**审计**：改配置的人写进 `logs/device-hub.log`（`系统配置被修改 by admin：{...}`）。
完整的操作审计表还没做（ROADMAP DH-24），现在只能靠日志追溯。

### 10.13 数据库结构变更（migration.sql）

`ddl-auto=update` 只会**加**表和列，改不了已有列：重命名、调整类型、加非空约束、
数据回填，它一样都不做。所以从 1.1.0 起，凡是动表结构的版本都要在升级包里带一份
`migration.sql`。

**执行时机是这个设计里最关键的一点**：脚本在服务启动时、**Hibernate 之前**执行。
放在之后会踩一个必然的坑——给已有表加 `not null` 列时，Hibernate 会先执行
`alter table ... add column x varchar(255) not null`，表里有数据时这句在 MySQL 上
会直接失败，服务起不来，报的还是一句没人看得懂的方言错误。

**它怎么跑到 Hibernate 前面的**：`MigrationInitializer` 挂在 `spring.factories` 里做
`ApplicationContextInitializer`，那时连 DataSource Bean 都还不存在，所以用裸 JDBC
从 `Environment` 读连接参数自己连。代价是不能用 JdbcTemplate，好处是顺序绝对靠前。

**执行规则**：

| 规则 | 说明 |
|---|---|
| 执行一次 | 成功过的版本记在 `schema_migration` 表，重启不再跑 |
| 失败会重试 | 失败记 `ok=false` + 原因，下次启动再试（改了脚本重新放进去就生效） |
| 前一个失败就停 | 后面的脚本大概率依赖前一个的结果，继续跑只会制造更多半截状态 |
| 不阻断启动 | 迁移失败服务照起——车间不能因为一次改表就没监控。但系统页会一直红着 |
| 状态可见 | 「系统 → 数据库结构」列出已执行/待执行/失败原因，能点开看每条语句 |

**允许执行什么**：正常 DDL、`insert`/`update` 数据回填、建索引。
**会被拒绝执行**（脚本原样保留在目录里，每次都提示，直到改对）：

- `drop database` / `drop schema`
- 不带 `where` 的 `delete`

理由很直白：这两类一条就能把客户几个月的产量和电费清空，不该由一段自动执行的脚本决定。
真要删，供应商远程、当面、手工做。`truncate` 和 `drop column` 不拦，但会在页面上黄字提示。

**写脚本的四条纪律**：

1. **可重入**：用 `create table if not exists`、`create index if not exists`；
   `insert` 前先 `delete` 或加唯一键判断。失败重试时不会因为"已经存在"再挂一次。
2. **只做数据，不改业务语义**：不要把 100 万行的一次性计算写进迁移，那应该在应用里做。
3. **一句一件事**：脚本会被逐句执行并记录第几句失败，一句里塞五个操作，出问题只能整体重来。
4. **改列名前先确认老版本已经没人用**。回滚只回滚 jar，**不回滚数据库**——
   1.1.0 把列名从 A 改成 B，回滚到 1.0.0 之后程序还在找 A，那是找不到的。
   带破坏性变更的版本，回滚预案要连数据一起想。

**手工补跑**：把脚本放进 `migrations/`（文件名就是版本号，如 `1.1.0.sql`）然后重启服务。
不需要改 `pending.env`，也不需要重新打包——这是现场救急最省事的路子。

### 10.14 交付包怎么做、怎么审

**一条命令**：

```bash
tools/make-dist.sh --build            # 构建 + 打包 + 审计
tools/make-dist.sh                    # 用现有的 target/device-hub.jar 重打
```

产出 `dist/device-hub-<版本>.zip`，包里只有六样东西：

```
device-hub-1.0.0/
├── device-hub.jar          程序
├── install.sh              一键安装
├── bin/apply-pending.sh    启动前应用升级包
├── bin/upgrade.sh          命令行升级/回滚
├── README.md               这份文档
├── VERSION.txt             版本、构建时间、jar 的 sha256
└── SHA256SUMS              逐文件校验清单
```

**有意不带的三样**：`application.yml`（配置由 `install.sh` 现场生成，只有一份模板，
不会出现"打印的密码和配置里写的不一致"）、`tools/`（签发和打包工具）、`data/`（你本机的数据）。

**审计是强制的，不通过就不产出 zip**。规则都在 `tools/audit-dist.sh`，可以单独跑：

```bash
tools/audit-dist.sh dist/device-hub-1.0.0        # 审目录
tools/audit-dist.sh dist/device-hub-1.0.0.zip    # 审压缩包
```

阻断项（任何一条命中就不能发）：

| 类别 | 具体 | 后果 |
|---|---|---|
| 私钥 | `private.key`、`*.p12/.jks/.pfx` | 拿到就能自己签升级包，等于能给你客户装任意程序 |
| 源码与工具 | `*.java`、`tools/`、`PackUpdate` | 等于把打包和签名的办法一起给了 |
| 客户数据 | `data/`、`updates/`、`backups/` | 带着你本机的演示数据或上一家的数据去见新客户 |
| 开发脚本 | `mock-*.js`、`*.bat`、`*.ps1` | 现场没人认识这些，出问题只会更乱 |
| 日志与库文件 | `*.log`、`*.mv.db`、`*.sql` | 同上，且可能泄露现场信息 |
| 配置模板 | `application.yml` | 两份模板会打架（见 10.6 / 安装脚本注释） |
| 换行符 | `.sh` 里有 CR 字节 | **Linux 上第一行就报 `command not found`** |
| 权限 | `.sh` 没有 755 | `./install.sh` 报 Permission denied |
| 校验和 | `SHA256SUMS` 对不上 | 客户核验时会以为包被篡改 |

jar 内部也查：必须有 `static/app/index.html`（否则页面 404）和 `META-INF/spring.factories`
（否则升级时数据库迁移不执行），且不能有 `.java`、私钥。

**这条审计不是形式主义**。写它的当天就抓到一个真问题：所有 `.sh` 都是 CRLF 换行——
在 Windows 上看不出任何异常，发到客户的 Ubuntu 上，`sudo ./install.sh` 第一行就报
`bash: $'\r': command not found`，客户的第一反应是"这软件装不上"。

**客户侧三步**：

```bash
unzip device-hub-1.0.0.zip && cd device-hub-1.0.0
sha256sum -c SHA256SUMS      # 先确认文件完整
sudo ./install.sh
```

> 别把两种包搞混：`make-dist.sh` 出的**安装包**给第一次部署用；
> `PackUpdate.java` 出的**升级包**给已装好的客户打补丁用（见 10.4）。
> 安装包里有 `install.sh`，升级包里没有。

## 十一、AI 早报（每天 7:00 自动出，能推微信）

一句话：**每天固定时间把「昨天」的情况写成人话发出去**，让老板和车间主任吃早饭时就知道厂里怎么样。

### 核心原则：AI 只润色，数据本地算

这是整个模块最重要的一条设计，决定了它能不能交付：

| 情况 | 结果 |
|---|---|
| 没配 API Key | 早报照出，用本地统计模板（数字一样准，只是没有分析和建议） |
| 客户断网 / API 欠费 / 模型名写错 | 自动降级到本地模板，**并写明失败原因** |
| 模型胡说（把数字写错） | 页面正文下面单独列 6 个统计卡片，并注明「数字以下方统计为准」 |

数据（在线台数、产量、停机、电费、需量、报警数）全部由 `DigestDataBuilder` 在本地算完，
再拼成一段紧凑事实喂给模型。模型只负责"把这些数字写成一段话"。
所以即使模型出问题，**也不会产生错误的生产数字**——这是能对客户负责的底线。

### 为什么不用 `@Scheduled(cron="0 0 7 * * ?")`

cron 是启动时写死的：客户在页面上把时间改成 7:30 就得重启；而且 7:00 正好在重启，
那一天就永久漏了。这里是「每分钟判断一次 + 记录最后运行日期」：

- 改时间立即生效
- 7:00 服务在重启，10:00 起来也会补发（补的仍然是昨天，日期不会错）
- 同一天只发一次，重启不会重复轰炸

### 配置（「早报」页 → 右上角 AI 设置）

| 字段 | 说明 |
|---|---|
| 接口地址 | 填到 `/v1` 为止，如 `https://api.deepseek.com/v1` |
| API Key | 形如 `sk-...` |
| 模型 | `deepseek-chat` / `qwen-plus` / `glm-4` / `llama3`（本地 Ollama） |
| 生成时间 | 默认 07:00 |
| 推送 | 复用报警通知渠道（企业微信/钉钉/飞书/Server酱/webhook） |

用的是 **OpenAI 兼容协议**，不绑定任何一家。客户内网出不去的话，可以指向局域网里的 Ollama
（`http://192.168.1.20:11434/v1`，模型填 `qwen2.5`），数据不出厂，这点在能碳类项目里很好讲。

「测试连接」会先保存再真发一句话过去，把模型的回复或报错原样显示——避免"填完不知道有没有生效"。

### 成本

每天一次，输入约 500~800 tokens（事实清单），输出 200~400 tokens。
按 DeepSeek 现价算，**一个月几毛钱到一两块**。早报不是高频功能，没必要为省这点 token 做缓存。

### 推送与免打扰

早报推送走 `AlarmNotifier.sendBulletin()`，**不受免打扰时段限制**：
免打扰是为了防止半夜被报警吵醒，早报本来就在固定时间发，被压住等于功能不存在。
但仍然尊重"通知总开关"和渠道的最小级别。

### 本地测试（不花钱）

```bash
node mock-ai.js     # 仓库根目录那个假 OpenAI 服务，监听 9098
```
然后在「AI 设置」里把地址填 `http://127.0.0.1:9098/v1`、Key 随便填，点测试连接。

### 实测（本机）

- 指向假服务：`source=AI`、`tokens=500`、正文为模型返回内容、6 个统计卡片正常、0 JS 报错
- 把地址改成不通的端口：`source=LOCAL`、`degraded=true`、错误原因显示 `ConnectException`，早报仍然出
- 未启用 AI（默认交付状态）：本地模板出报，数字与报表页一致（产量 2606 件 / 电费 534 元 / 需量 300 kW）

## 十二、车间大屏（挂墙电视，不用登录）

看板屏地址：**`http://服务器IP:8080/screen.html`**；故障屏地址：**`http://服务器IP:8080/fault.html`**。
主界面顶栏也有「大屏」入口（新标签打开）。两块屏免登录、同一套数据接口 `/api/screen/snapshot`，
顶栏各有一个切换按钮可以互跳；挂墙电视没鼠标时用 `?rotate=N`（N=分钟数）自动轮流切换，
例如 `http://服务器IP:8080/screen.html?rotate=10` —— 看板放 10 分钟自动跳故障屏，故障屏放 10 分钟再跳回来，
右上角有倒计时。

**不需要登录**——这是刻意的：大屏是挂在车间墙上的电视，要输密码等于没法用。
所以它的数据接口 `/api/screen/snapshot` 只返回聚合数字和「设备名 + 状态」，
点表、API Key、接口地址一概不出现（ScreenController 注释里写了这条红线）。
家里那台主界面仍然要登录，权限边界没变。

### 屏上有什么

| 区域 | 内容 | 口径 |
|---|---|---|
| 6 个 KPI | 今日产量 / 稼动率 / 停机时长 / 停机次数 / 在线设备 / 未处理报警 | 和报表页同源：稼动率、停机时长按状态秒数算；停机次数来自停机/离线告警 |
| 设备状态分布 | 环形图：运行/待机/停机/报警/离线 | 离线单独算，没配状态点的设备按"运行"处理，不显示成假停机 |
| 今日产量趋势 | 每小时柱状图，标峰值 | 缺的小时补 0——停机就是 0，不是没数据 |
| 实时报警 | 按严重→一般排序，超一屏自动翻页（8 秒） | 不足 1 分钟显示"刚刚" |
| 停机原因 | Top 6，按时长排 | 复用报表的停机原因统计 |
| 设备状态 | 全部设备的芯片墙 | 绿运行 黄待机 红停机 灰离线 |
| **故障维修看板** | 有未恢复报警时自动替换「停机原因」区，逐台轮播 | 见下 |
| 底部滚动条 | 最新动态 | 无报警时显示产量播报 |

### 故障维修看板（给维修工的那一块）

只要存在未恢复报警，左下角自动变成**维修卡**，一张卡一台设备：

1. **报警明细**：级别、规则名、人话消息、触发值/阈值、持续时长
2. **通讯与端口**：协议、`IP:端口`（或串口/波特率）、从站号、轮询周期、超时、在线状态、最后错误——
   维修第一件事是确认链路通不通，这些就是判断依据
3. **伺服/PLC 报警字**：点表里 `role=alarm` 的点位（如伺服的报警码寄存器），
   非零即报警码，直接显示数值。具体代码含义查对应品牌手册（三菱 AL.xx、汇川 Er.xx 各不相同），
   系统不猜，猜错一次比不显示严重得多
4. **AI 故障分析**：把上面 1~3 的事实喂给模型（OpenAI 兼容接口，和早报共用一套配置），
   输出可能原因、排查步骤、风险提示

三条纪律：

- **AI 只润色，事实本地算**：报警内容、通讯参数都是系统自己的数据，模型只负责组织成人话；
  没配 AI / 断网 / 欠费时自动退回「本地建议」（按故障类型给通用排查步骤），并标明来源，看板永远有内容
- **签名变了才重新分析**（报警集合 + 通讯状态 + 报警字）。千万别把实时点位值放进签名——
  温度每秒都在跳，AI 会被迫每 3 秒分析一次，token 白烧，看板上永远显示"生成中"
- **AI 不猜报警码**。代码表各家不一样，让模型猜"33 号报警是什么"是在制造事故

### 几个刻意的设计

1. **零外部依赖**。不引 ECharts/字体/任何 CDN——车间电视经常没外网，白屏一次客户就不信这套系统了。图表全部手写 SVG/CSS。
2. **断网不清屏**。拉数据失败时保留最后一屏，连续两次失败才在中间压一条"连接中断"，网络恢复自动消失。大屏变白板比数据旧 10 秒严重得多。
3. **3 秒服务端缓存**。车间挂 3 块屏也是每 3 秒算一次，不会把数据库打三遍。
4. **5 秒自刷新 + 回到前台立即刷**。电视浏览器休眠唤醒后数据是旧的，切回可见时马上补一枪。
5. 每小时柱子只有**当前小时**高亮 + 数值常显，避免 24 个数字糊成一团。

### 报警码字典（伺服原始码 → 文字含义）

维修卡的报警字区不只显示裸码——按设备上配置的**品牌**查内置字典，翻译成名字、原因、处理方法：

```
伺服 / PLC 报警字 · 三菱伺服（MR-JE / MR-J4 系列）
alarm = 33（过电压）
过电压：母线电压过高（减速过快/电网电压偏高）｜处理：延长加减速时间；测电网电压…
```

**品牌在设备表单里配**（「伺服/PLC 品牌」下拉），目前内置：

| 品牌 | 收录 | 说明 |
|---|---|---|
| 三菱伺服 | MR-JE / MR-J4 常用 20 个码（欠压/过压/过流/过载/编码器/再生/通讯…） | 文件 `alarmcodes/mitsubishi-servo.json` |
| 台达伺服 | ASDA-B2/B3 常用 14 个码 | `alarmcodes/delta-servo.json` |
| 安川 / 松下 / 汇川 / PLC | 下拉可选但暂无内置表 | 显示原始码 + 「未收录，查品牌手册」 |

**两个如实的边界**：

1. 只收了**现场出现频率最高**的码，不是全量手册翻译。没收录的码显示原始值并提示查手册——
   宁可少翻，不可翻错；想补充就往 `alarmcodes/<品牌>.json` 加条目、`index.txt` 加一行文件名，重启生效。
2. **PLC 报警字没有内置表，也做不了**——那是设备厂程序里自定义的位，每台机器都不同。
   这类要么按现场点表把位含义整理成字典文件，要么靠 AI 分析时结合上下文判断。

字典同时通过 `GET /open/v1/{code}/alarms` 的 `plcWords` 字段给 MES，
对接方不用自己维护码表。

### 故障屏（独立大屏，整面墙给维修工）

看板屏里维修卡只有左下角一块、一次只轮播一台；车间里故障多、维修人员盯着看的时候，
直接开**故障屏**：`http://服务器IP:8080/fault.html`。

- **一页最多 4 张维修卡（2×2 铺满整屏）**，每张卡左右分栏：
  左边报警明细 + 通讯与端口，右边伺服/PLC 报警字（含字典翻译的原因/处理）+ AI 分析。
  报警明细每卡最多 4 条，超出以最严重的在前。
- 超过 4 台故障时 **15 秒自动翻页**，右上角显示「第 x/y 页」。
- **没有故障时全屏绿字「当前无设备故障」**，不放空面板假装在干活。
- 顶部 4 个 KPI：未处理报警、故障设备、离线/停机、在线设备。
- 其余纪律与看板屏一致：免登录、只读、5 秒自刷新、断网不清屏、零外部依赖、AI 只润色不猜码。

**两块屏怎么分工**：看板屏给全车间看产量和整体状态，故障屏给维修工位/维修班组看细节。
可以各挂一台电视，也可以一台电视 `?rotate=N` 轮着放。

### 现场怎么挂

```text
看板屏：电视 → Chrome → F11 全屏 → 开机自启指向 http://服务器IP:8080/screen.html
故障屏：维修工位电视 → 同上 → http://服务器IP:8080/fault.html
单台轮换：两屏地址后加 ?rotate=10（10 分钟互切，右上角倒计时）
```

页面按 1920×1080 设计，用 vw/vh 缩放，4K 电视和迷你屏都不会溢出（实测无横向/纵向滚动）。

## 十三、功能路线图与页面结构

这一节回答两个问题：**该做哪些功能、页面怎么组织**。

原则只有一条：
**功能可以对标任何成熟产品，代码和界面必须自己写。**

功能清单、业务流程、报表指标属于「思想」，不受版权保护；
源代码、页面设计稿、图标素材、文案属于「表达」，抄了就是侵权。
抄思路是学习，抄代码是给自己埋雷——尤其是 AGPL 的项目，
你把它的代码合进来，整个系统都得跟着开源，辛苦做的商业保护直接作废。

### 演示数据与全功能冒烟（每做完一个功能都跑一遍）

```bash
python tools/seed-demo.py     # 铺一套像真工厂的数据（幂等，重复跑只补缺的）
python tools/smoke-all.py     # 每个页面背后的接口跑一遍，输出 过/挂/跳过
```

- `seed-demo.py`：9 个商品（成品/原材料/外购件）、3 个仓库、3 个供应商 + 3 个客户；
  采购 6 种状态、销售 6 种状态、库存 7 类单据（采购入库/采购退货/销售出库/销售退货/
  其他出入库/调拨/盘点）各铺一张。按**编码**和备注里的**场景标签**判重，
  重复执行不会把库存刷爆；只创建自己的数据，不删不改客户已有单。
- `smoke-all.py`：页面可达 + 设备/报警/能耗/报表/AI/系统/ERP 基础/采购/库存/销售
  共 50+ 项读接口；写路径（建单→取消、入库→作废）**每天只跑一次**，避免留一堆废单。
- `tools/selftest.py` 继续管底层契约与权限（40 条断言，自建自删），三者分工不同。

**纪律**：每完成一个功能 → `seed-demo.py` → `smoke-all.py` → 全绿再提交。
演示数据能在界面上直接看到"每种状态长什么样"，比对着空页面点一小时更有用。

为什么这么排：

- **设备监控是主战场**，厂里的人一天看几十次，所以放第一个页签、卡片墙 + 分页
- **能耗分析是给老板看的**，一个月看一次，但它决定要不要加钱，所以放第二个
- **报警是给班组长看的**，出事才看，所以放第三；但顶栏留了铃铛，不用点进来也知道有没有事
- **报表是月底交差的**，一个月打开一次，放最后；导出按钮一定放在第一屏，客户找三次就烦了

**该补的（按客户掏钱的意愿排）**

1. **多接入点**——AI 配置支持多套接入点（本地/云端各一套，按场景切换）。
2. **AI 运维增强（DH-48）**——自然语言出报表、异常解读。3. **历史归档**——内存曲线换成 MySQL 分表或 TDengine，设备到 2000 台再动。
4. **OEE 完整版**——要客户提供计划产量和不良数才能算真 OEE，硬凑数据不如不算。
5. **电费月报并入报表**——现在电费在能耗页，报表里只有产量，客户交月报要跑两个页面。

**别做的**

- **碳盘查、绿色工厂申报**——要行业 know-how 和咨询资质，不是写代码能解决的。
  真接到这种单，让客户去买专业 EMS 的授权，你做实施和现场接入，赚该赚的那份。
- **自研时序数据库 / 消息队列**——用现成的。
- **做成 SaaS 多租户**——你一个人运维不了，客户也不放心把生产数据放你服务器上。
- **做硬件**——不做电子产品是对的，深耕协议和现场接入。

### 报价锚点

同一套东西，说法不同，价格差三倍：

| 客户听到的 | 他觉得值多少 |
|---|---|
| 「能看设备状态」 | 3~5 万（一个看板而已） |
| 「能看每台机器的产量和停机」 | 8~12 万（跟产能挂钩了） |
| 「能算每台机器每个月多少电费，按峰谷分时」 | 15~25 万（直接对上财务的账） |
| 「还能出月报、能对接他的 ERP」 | 30 万+（进入他的管理流程了） |

功能没变，变的是「这东西跟谁的钱包有关」。
