# 采集规模压测报告（1000 台设备）

> 生成日期：2026-11-07
> 工具：`tools/bench-collect-scale.sh`（L1 调度层）＋ `CollectDbScaleBench`（L2 写库层）
> 场景矩阵：S1 零延迟 / S2 30ms / S3 50ms / S4 100ms / S5 30ms+抖动 / S6 负向对照
> 环境：Windows 11，12 核，JDK 17.0.20，MySQL 8.4.11（`devicehub_perf` 压测专用库）

---

## 一句话结论

**1000 台设备 × 1 秒周期，在当前配置下不达标。**
两个瓶颈，**都不是「线程不够」这么简单**：

| 瓶颈 | 实测 | 加线程有用吗 |
|---|---|---|
| **采集线程池 32 太小** | I/O 30ms 时就需要 34 个线程（实测丢轮 0.124% 但已被判不达标）；I/O 50ms 时需要 54 个（实测轮间隔 1606ms、丢轮 38.0%） | **有用**：64 线程时 I/O 50ms ⇒ 轮间隔 1001ms、丢轮 0.100% |
| **`ProdRollup.todayOutputOf` 全局锁 + 每轮 2 次查库** | S7（只给 DB 加 1ms）⇒ 轮间隔 2686ms、丢轮 62.9%；**容量公式在这里给出乐观的错误答案** | **无用**（只会让更多线程挤同一把锁） |

⇒ **加线程能解决 I/O 瓶颈，解决不了锁瓶颈；而锁瓶颈一旦出现，周期会非线性恶化。**

## 一、怎么测的（两层）

| 层 | 测什么 | 真实的部分 | 替身的部分 |
|---|---|---|---|
| **L1 调度层** | 1000 台 × 共享线程池能不能达成 1 秒周期 | `CollectScheduler` + `DeviceCollector` + 真实线程池 + 真实 WS 广播路径 | 协议驱动（可配 I/O 延迟）、`ProdRollup`（可配 DB 耗时 + **忠实复刻 monitor 语义**） |
| **L2 写库层** | 全局锁 + 真实查库的成本 | **真实 MySQL 8.4.11**、真实 SQL、真实索引、真实有界连接池（借用/归还） | **L2 用的 JDBC，不是 JPA** ⇒ JPA 的实体装配与事务开销**没测到**（真实值 ≥ L2 的值） |

⇒ **两层合起来仍是对真实系统的乐观估计**。

## 二、L1 调度层实测

池大小 32，目标周期 1000ms，1000 台设备，预热 30s + 测量 120s。

> ⚠️ **本表由 `tools/bench-report.mjs` 从压测日志自动生成，勿手抄**
> （手抄过一次，把 S1 的数字安到了 S2 行上，而 S2 实际是失败的 ⇒ 报告偏乐观了一档。）

| 场景 | 说明 | 轮间隔 P50/P95/P99 (ms) | 丢轮率 | 采集线程数 | 容量公式 N | 判定 |
|---|---|---|---|---|---|---|
| S1 | 零延迟反向对照 | 1001 / 1002 / 1002 | 0.047%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 0.0ms / 1000ms) = 1  (池大小 32) | ✅ 通过 |
| S2 | 30ms（局域网快设备） | 1001 / 1003 / 1013 | 0.124%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 33.0ms / 1000ms) = 34  (池大小 32) | ❌ **不达标** |
| S3 | 50ms（现场常见） | 1606 / 1637 / 1643 | 37.968%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 53.0ms / 1000ms) = 54  (池大小 32) | ❌ **不达标** |
| S4 | 100ms（重负载） | 3175 / 3209 / 3220 | 68.482%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 103.0ms / 1000ms) = 104  (池大小 32) | ❌ **不达标** |
| S5 | 30ms + 抖动 0~30ms | 1496 / 1512 / 1519 | 33.153%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 62.0ms / 1000ms) = 63  (池大小 32) | ❌ **不达标** |
| S7 | DB 1ms（验证全局锁排队） | 2686 / 2806 / 2870 | 62.857%（目标 <= 0.5%） | 共 32（池 32） | ceil(1000 × 3.5ms / 1000ms) = 4  (池大小 32) | ❌ **不达标** |
| S3P | 50ms + 64 线程（加线程对照） | 1001 / 1002 / 1003 | 0.100%（目标 <= 0.5%） | 共 64（池 64） | ceil(1000 × 53.0ms / 1000ms) = 54  (池大小 64) | ✅ 通过 |
| S6 | 负向对照（常量值驱动，必须变红） | — | — | — | — | ✅ 如期变红（护栏生效） |

### 容量公式：**用来估算够不够**，但不是精确预测

```
N = ceil(设备数 × P95(单轮线程占用) / 目标周期)
```

⚠️ **这个公式用 P95，而稳态吞吐由「平均」决定** ⇒ 它算出的 N 是**上界**（偏保守），
**不是**「池大小 = N 就刚好够」。实测对照：

| 场景 | 公式算出的 N | 理论周期（1000×P95/32） | 实测轮间隔 P50 | 差异 |
|---|---|---|---|---|
| S3 | ceil(1000 × 53ms / 1000ms) = 54 | 1656ms | 1606ms | 差 3.1% |
| S4 | ceil(1000 × 103ms / 1000ms) = 104 | 3219ms | 3159ms | 差 1.9% |
| S5 | ceil(1000 × 62ms / 1000ms) = 63 | 1937ms | 1496ms | **差 22.8%** |

⇒ **S5 的偏差很大**（P95 被抖动放大，而稳态靠均值）⇒
**这个公式只能用来判断「差多少量级」，不能当精确预测**；加抖动时尤其不准。

⇒ 现场定值的正确做法：**按公式估一个下界，再实测调整**（`tools/bench-collect-scale.sh`
可以直接跑目标规模与目标周期，报告里的 P50/P95/P99 与丢轮率就是定值依据）。

### ⚠️⚠️ **容量公式看不到「排队等待」⇒ 它在锁瓶颈场景下会给出乐观的错误答案**

S7（I/O=0、只给每次 `todayOutputOf` 加 1ms 的 DB 成本）实测：

```
轮间隔 P50 = 2686ms（目标 1000ms）、丢轮 62.9%
而容量公式算出来是 N = ceil(1000 × 3.5ms / 1000ms) = 4  ⇒ 「4 个线程就够」
```

**公式说 4 个线程够，实际 32 个线程都跑出 2686ms 的周期。**
⇒ 原因：公式只算「线程被占用的时间」，**不算「等锁排队的时间」**。
⇒ **一旦锁成为瓶颈（而不是 I/O），这个公式就完全失效。**
⇒ 所以：**先看是不是锁瓶颈（看 S7 与锁等待 P99），是锁瓶颈就别用这个公式定线程数** ——
去锁才是正解。

### 「加线程」这条路径被证实

S3 同样 I/O=50ms，只把池从 32 调到 64：轮间隔 1606ms → **1001ms**，丢轮率 37.9% → **0.078%**。

## 三、L2 写库层实测（真实 MySQL）

1000 台设备各调一次 `todayOutputOf()`（= 2 次查库），真实 `devicehub_perf` 库
（1000 台设备 + 每台 24 行小时产量），连接池 10（与 `application.yml` 的 `maximum-pool-size` 一致）。

```
单次 todayOutputOf（2 次查询）: P50=0.715ms  P95=0.971ms  P99=1.155ms
=> 1000 台**串行**（synchronized 全局锁）= 715 ms  vs 目标周期 1000 ms

1000 台并发一轮: 910ms / 673ms / 696ms
全局锁等待:      P50=382ms  P95=787ms  P99=883ms
连接池 10 个:    借用 3000 次，**耗尽 0 次**
```

### 结论

1. **`todayOutputOf` 是全局串行点**：`ProdRollup.java:396` 方法级 `synchronized`，
   锁内含 `deviceService.byCode()`（1 次查库）+ `repo.findByDeviceCodeAndHourStartBetween()`（1 次查库）。
   ⇒ 1000 台时**仅这一条路径就占掉 71.5% 的锁时间**（1000 × 0.715ms），
   实测**锁等待 P99 = 883ms**（= 一次采集里最慢的那台等了近 0.9 秒）。
   ⚠️ **这 71.5% 是下界，不是全部**：`scan()`（每秒）与 `checkpoint()`（每 60 秒）
   也持**同一把** `ProdRollup` monitor，且 `scan()` 要遍历全量设备
   ⇒ 真实锁占用率更高，**本轮未量化**（见第六节待办 1）。
   ⚠️ **不要把 P99 当成「88% 的时间在等锁」** —— P99 是分位数不是占比；
   要算占比必须用「总锁等待时间 ÷ 总墙钟时间」，本轮没测那个量。
2. **连接池 10 个够用**（0 次耗尽）——因为锁已把并发串行化，DB 侧压力不大。
   ⇒ **加线程不会缓解这一层，只会让更多线程挤在同一把锁上。**
   ⚠️ 这条结论**依赖「锁已经把并发串行化」这个前提** ⇒ 一旦把锁去掉（第六节方案），
   连接池就成了新瓶颈 ⇒ **去锁方案必须连带做「去锁后的连接池压测」**。
3. 单看 DB 层，1000 台一轮 673–910ms **勉强塞进 1 秒**，但**余量只剩 10–30%**，
   再叠加真实 PLC 的网络抖动与其它定时任务（`EnergyRollup` 每秒扫全量、
   `AlarmEngine` 每 2 秒、`ErpProdInboundService` 每 10 秒）⇒ **不稳健**。

## 四、为什么每轮都会调 `todayOutputOf`（D-1 陷阱，已实测）

`DeviceCollector.pushValues()` 的顺序是：

```java
if (changed.isEmpty()) { return; }        // ← 提前返回
...
msg.put("todayOutput", rollup.todayOutputOf(device.getCode()));   // ← 在返回之后
```

`PointValue.sameAs()` **只比较 value 与 quality，不比较 ts** ⇒
**假驱动若返回常量值，第二拍起 `changed` 恒空 ⇒ `todayOutputOf` 一次都不会被调用。**

⚠️ 这意味着：**用常量值假驱动做压测，会完全测不到全局锁这条最热的路径，而压测照样绿。**

S6 负向对照已实测证实：常量值场景下 `todayOutputOf` 调用 **0 次**（期望 ≥ 1800）。
⇒ `CollectScaleBench` 用**递增计数**（`--const-values` 只用于负向对照），
并断言 **`calls : reads ≈ 1.0`**。

⚠️ **「每台每轮必调」是上界，不是恒等**：只有**点值发生变化**时才会调。
本压测的假驱动每拍都变值 ⇒ 必然每轮调用 ⇒ 这是**真实 PLC 上界**（现场若某设备
读数长期不变，则它的调用次数更少 ⇒ 锁压力更小）。真实值需现场实测。

## 五、给现场的容量建议

⚠️ **这张表只在「瓶颈是 I/O」时成立**（即锁还没成为瓶颈）。
若是锁瓶颈（S7 那种情况），**加线程无效**，必须先按第六节去锁。

| 现场规模 | 建议 `collect.threads` | 依据（I/O 50ms、周期 1000ms） |
|---|---|---|
| ≤ 100 台 | 16（默认 32 够用） | 100 × 50ms / 1000ms = 5，取 2 倍余量 |
| ≤ 300 台 | 32 | 300 × 50ms / 1000ms = 15 |
| ≤ 500 台 | 48 | 500 × 50ms / 1000ms = 25 |
| 1000 台 | **96–128** | 1000 × 50ms / 1000ms = 50，取 2 倍余量 |

⚠️ **但先改 `todayOutputOf` 的查库与锁，再谈加线程** ——
加线程只解决 L1，解决不了 L2（而 L2 的余量更薄、恶化更非线性）。
⇒ 顺序：**先确认瓶颈是哪一层（跑 S7 看锁等待）→ 是锁就去锁 → 再按上表定线程数。**

## 六、待办（下一轮）

| # | 事项 | 依据 | 风险 |
|---|---|---|---|
| **1** | **L3 层压测：`scan()`/`checkpoint()` 持锁扫全量的真实成本**（它们与 1000 个 `todayOutputOf` 争**同一把** monitor ⇒ **这才是真正的第一竞争者**，本轮完全没测） | L2 只测了 `todayOutputOf` 一条路径 | —（先测，才知道改什么） |
| **2** | **`todayOutputOf` 的已落库历史小时部分改为缓存**（见下方方案） | L2：仅这一条路径就占 71.5% 的锁时间 | 中（动生产口径路径） |
| **3** | **`collect.threads` 默认值与文档按规模调整** | L1 容量公式 | 低（已是可配置项） |
| **4** | **`pushValues` 的 WS 广播量**（1000 台 × 每轮 × 每客户端；`WsHandler.broadcast` 对每个会话调 `sendMessage`，**在调用线程上执行**）在有看板时可能成为第三个瓶颈 | L1 未测（无客户端时 `broadcast` 走 `sessions.isEmpty()` 早返回分支，零成本） | 待测 |
| **5** | **去锁后的连接池压测**（L2 的「池够用」依赖「锁已把并发串行化」这个前提 ⇒ 一旦去锁，池就是新瓶颈） | 同上 | — |

### 待办 2 的方案选型（**先按写失效，不要按时间失效**）

| 方案 | 做法 | 评价 |
|---|---|---|
| **Alt-1（推荐）** | 复用仓库已有的 `todayByDevice` 聚合 + `findByDeviceCodeInAndHourStartBetween`（批量查库），让 `scan()` **每秒批量算一次**并用 `AtomicReference` 发布**不可变快照**；`todayOutputOf` 读快照 + 读 `buckets` 的实时增量 | 数据新鲜度与现有「秒级」语义一致；**查库从 1000 次/秒 → 1 次/秒**（批量） |
| **Alt-2（按时间失效）** | TTL 60 秒缓存（依据：`checkpoint` 每 60 秒落库 ⇒ 两次落库之间 DB 值不变） | ⚠️ **把「数据会不会变」押在时间上**。若 `checkpoint` 失败或 `scan` 改了历史小时，缓存就会给出**过期值** ⇒ 客户的「今日产量」会与报表对不上 |
| **Alt-3（按写失效）** | 在 `flush()`（落库成功）与 `purgeByCode()`（删设备）处**显式失效**缓存 | ✅ 数据正确性由**写事件**保证，不依赖时钟 ⇒ 比 Alt-2 安全 |

⚠️ **并发正确性（两个方案都必须处理）**：
- `ProdHourly` 是**可变对象**（有 setter），`scan()` 线程会改它 ⇒ **不能直接无锁读 `buckets` 里的对象**
  （可能读到「runSec 是新的、output 是旧的」这种不一致组合）⇒
  要么发布**不可变快照**（`AtomicReference<Map<String,Double>>`），要么在读时复制。
- `buckets` 本身是 `ConcurrentHashMap` ⇒ **拿到 map 引用**是安全的，**不安全的是拿到的元素**。
- `todayOutputOf` 的**生产代码调用方只有一处**（`DeviceCollector.pushValues`）
  ⇒ 改造的爆炸半径小 ⇒ 但也意味着**必须补单测**（当前生产代码对 `todayOutputOf`
  **零单测覆盖** ⇒ 改造前必须先补，否则改坏了没人知道）。

## 七、这个压测**测不到**什么（诚实清单）

1. **真实 PLC 的网络抖动与重传** —— L1 的 I/O 延迟是固定值/人工抖动，没有真实的丢包重传分布。
2. **JPA 实体装配与事务开销** —— L2 用 JDBC，真实值 **≥** L2 的值 ⇒ L2 的结论是乐观下界。
3. **Hikari 的连接借用/归还开销** —— L2 模拟了池的借用与归还语义，但没用真的 Hikari。
4. **WS 广播的真实成本** —— L1 没有客户端连接 ⇒ `broadcast` 走的是 `sessions.isEmpty()` 的早返回分支。
5. **其它定时任务与采集争锁** —— `ProdRollup.scan()`（每秒）与 `checkpoint()`（每 60 秒）
   持**同一把** `ProdRollup` monitor，`scan()` 要遍历全量设备（1000 台 × N 点）
   ⇒ **这才是真正的第一竞争者**，而本轮**只测了 `todayOutputOf` 一条路径**（L3 层缺口）。
   ⚠️ 注意：`EnergyRollup`/`AlarmEngine`/`ErpProdInboundService` 各自 `synchronized`
   在**自己的实例**上 ⇒ **它们不共享 `ProdRollup` 的 monitor** ⇒ 不是同一把锁的竞争者
   （但它们仍会抢 CPU 与连接池）。
6. **GC 压力下的表现** —— 堆增长在 120 秒窗口内未稳定，可能掩盖长跑后的 GC 停顿。
7. **多实例部署** —— 本轮是单进程。

## 八、护栏（防「压测绿了但什么都没验」）

| # | 护栏 | 怎么验的 |
|---|---|---|
| 1 | **calls : reads ≈ 1.0** | 断言比值 < 0.98 即红 |
| 2 | **负向对照 S6 必须变红** | 常量值驱动 ⇒ 路径没走到 ⇒ 必须红（`--expect-fail`） |
| 3 | **线程数必须在 shutdown 之前数** | 关掉池之后数只会得到 0，而「0 ≤ 池大小」恒成立 ⇒ 假绿 |
| 4 | **逐台判定，不许加总** | 「加总 > 0」会掩盖个别设备饿死 ⇒ 公平性测试逐台断言轮数 |
| 5 | **公平性护栏有变异验证** | 注入「部分设备首次执行推迟 500 倍」⇒ 测试红且诊断指对（「有 3 台设备一轮都没被采集到」）⇒ 还原后绿 |
| 6 | **编译失败必须硬校验** | 脚本曾把 mvn 输出管进 grep 再取 `$?` ⇒ **管道退出码是 grep 的** ⇒ 5 个场景全部 `ClassNotFound` 而汇总只说「未通过」 |
| 7 | **CPU 读不到就说读不到** | 反射调 `getProcessCpuTime` 被 JDK 模块系统拦 ⇒ 读到 -1，不能当成 0% |
| 8 | **轮间隔样本必须逐台覆盖** | 固定长度数组（设备数 × 39）⇒ 120 秒里需要 ~119000 个间隔，数组只有 39000 ⇒ **后 672 台设备的间隔一个都没进统计**，且**不报错** ⇒ 分位数只覆盖 1/3 的设备却看着正常。现在动态扩容 + 报告「参与统计的设备数」+ 断言覆盖度 |
| 9 | **报告数字由脚本生成，不许手抄** | 手抄过一次：把 S1 的数字安到 S2 行上，而 **S2 实际是失败的** ⇒ 报告偏乐观一档。现在 `tools/bench-report.mjs` 从日志生成表格，`--check` 逐行比对 ⇒ **篡改报告数字会红**（已变异验证：篡改 ⇒ 红 ⇒ 还原 ⇒ 绿）|
| 10 | **解析失败不能当成「没有」** | `bench-report.mjs` 的正则二次转义 ⇒ 字段抓不到 ⇒ 表格显示「—」⇒ 看着像「没这项」，实际日志里有。现在 label 传正则片段、不二次转义 |
| 11 | **锁等待的判定分支必须被交付场景覆盖** | S1~S5 的 DB 成本都是 0 ⇒ 那条「锁等待 P99 > 50ms ⇒ 瓶颈是 monitor」的护栏**从不触发** ⇒ 等于装饰性的。现在加 **S7**（DB 1ms）专门验证它 |
