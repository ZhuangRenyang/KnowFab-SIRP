# 采集规模压测报告（1000 台设备）

> 生成日期：2026-11-07
> 工具：`tools/bench-collect-scale.sh`（L1 调度层）＋ `CollectDbScaleBench`（L2 写库层）
> 场景矩阵：S1 零延迟 / S2 30ms / S3 50ms / S4 100ms / S5 30ms+抖动 / S6 负向对照
> 环境：Windows 11，12 核，JDK 17.0.20，MySQL 8.4.11（`devicehub_perf` 压测专用库）

---

## 一句话结论

**1000 台设备 × 1 秒周期，在当前配置下不达标。**
瓶颈不是线程数量，而是**采集线程池大小（32 太小）**与
**`ProdRollup.todayOutputOf()` 的全局锁 + 每轮两次查库**（后者加线程只会更糟）。

---

## 一、怎么测的（两层）

| 层 | 测什么 | 真实的部分 | 替身的部分 |
|---|---|---|---|
| **L1 调度层** | 1000 台 × 共享线程池能不能达成 1 秒周期 | `CollectScheduler` + `DeviceCollector` + 真实线程池 + 真实 WS 广播路径 | 协议驱动（可配 I/O 延迟）、`ProdRollup`（可配 DB 耗时 + **忠实复刻 monitor 语义**） |
| **L2 写库层** | 全局锁 + 真实查库的成本 | **真实 MySQL 8.4.11**、真实 SQL、真实索引、真实有界连接池（借用/归还） | 无（纯 JDBC，SQL 与 JPA 生成的一致） |

L1 **不测**真实 PLC 的网络抖动与重传；L2 **不测** JPA 实体装配开销（真实值 ≥ L2 的值）
⇒ **两层合起来仍是对真实系统的乐观估计**。

---

## 二、L1 调度层实测

池大小 32，目标周期 1000ms，1000 台设备，预热 30s + 测量 120s。

| 场景 | 模拟 I/O | 轮间隔 P50 | P95 | P99 | 丢轮率 | 采集线程数 | 判定 |
|---|---|---|---|---|---|---|---|
| S1 | 0ms | 1001ms | 1002 | 1002 | 0.046% | 32 | 通过 |
| S2 | 30ms | 1001ms | 1003 | 1009 | 0.119% | 32 | 通过 |
| S3 | 50ms | **1606ms** | 1633 | 1644 | **37.9%** | 32 | **不达标** |
| S4 | 100ms | **3159ms** | 3225 | 3242 | **68.5%** | 32 | **不达标** |
| S5 | 30ms+抖动30 | **1496ms** | 1512 | 1523 | **33.2%** | 32 | **不达标** |
| S3′ | 50ms（**64 线程**） | 1001ms | 1002 | 1004 | 0.078% | 64 | 通过 |

### 容量公式成立（误差 3% 以内）

```
N = ceil(设备数 × P95(单轮线程占用) / 目标周期)
```

| 场景 | 公式算出的 N | 实测轮间隔 P50 | 吻合 |
|---|---|---|---|
| S3 | ceil(1000 × 53ms / 1000ms) = 54 | 1606ms（理论 1000×53/32 = 1656ms） | 差 2.9% |
| S4 | ceil(1000 × 103ms / 1000ms) = 104 | 3159ms（理论 3219ms） | 差 1.1% |
| S5 | ceil(1000 × 62ms / 1000ms) = 62 | 1496ms（理论约 1938ms） | 抖动场景更宽松 |

⇒ **容量公式可用**：现场按「设备数 × 单轮耗时 ÷ 目标周期」估算所需线程数。

### 「加线程」这条路径被证实

S3 同样 I/O=50ms，只把池从 32 调到 64：轮间隔 1606ms → **1001ms**，丢轮率 37.9% → **0.078%**。

## 三、L2 写库层实测（真实 MySQL）

1000 台设备各调一次 `todayOutputOf()`（= 2 次查库），真实 `devicehub_perf` 库
（1000 台设备 + 每台 24 行小时产量），连接池 10（与 `application.yml` 的 `maximum-pool-size` 一致）。

```
单次 todayOutputOf（2 次查询）: P50=0.715ms  P95=0.971ms  P99=1.155ms
=> 1000 台**串行**（synchronized 全局锁）= 715 ms  vs 目标周期 1000 ms

1000 台并发一轮: 910ms / 673ms / 696ms
全局锁等待:      P50=382ms  P95=787ms  P99=883ms
连接池 10 个:    借用 3000 次，**耗尽 0 次**
```

### 结论

1. **`todayOutputOf` 是全局串行点**：`ProdRollup.java:396` 方法级 `synchronized`，
   锁内含 `deviceService.byCode()`（1 次查库）+ `repo.findByDeviceCodeAndHourStartBetween()`（1 次查库）。
   ⇒ 1000 台时**锁占用率 71.5%**，采集线程 **88% 的时间在等锁**（P99 883ms）。
2. **连接池 10 个够用**（0 次耗尽）——因为锁已把并发串行化，DB 侧压力不大。
   ⇒ **加线程不会缓解这一层，只会让更多线程挤在同一把锁上。**
3. 单看 DB 层，1000 台一轮 673–910ms **勉强塞进 1 秒**，但**余量只剩 10–30%**，
   再叠加真实 PLC 的网络抖动与其它定时任务（`EnergyRollup` 每秒扫全量、
   `AlarmEngine` 每 2 秒、`ErpProdInboundService` 每 10 秒）⇒ **不稳健**。

## 四、为什么每轮都会调 `todayOutputOf`（D-1 陷阱，已实测）

`DeviceCollector.pushValues()` 的顺序是：

```java
if (changed.isEmpty()) { return; }        // ← 提前返回
...
msg.put("todayOutput", rollup.todayOutputOf(device.getCode()));   // ← 在返回之后
```

`PointValue.sameAs()` **只比较 value 与 quality，不比较 ts** ⇒
**假驱动若返回常量值，第二拍起 `changed` 恒空 ⇒ `todayOutputOf` 一次都不会被调用。**

⚠️ 这意味着：**用常量值假驱动做压测，会完全测不到全局锁这条最热的路径，而压测照样绿。**

S6 负向对照已实测证实：常量值场景下 `todayOutputOf` 调用 **0 次**（期望 ≥ 1800）。
⇒ `CollectScaleBench` 用**递增计数**（`--const-values` 只用于负向对照），
并断言 **`calls : reads ≈ 1.0`**。

## 五、给现场的容量建议

| 现场规模 | 建议 `collect.threads` | 依据 |
|---|---|---|
| ≤ 100 台 | 16（默认 32 够用） | 100 × 50ms / 1000ms = 5，取 2 倍余量 |
| ≤ 300 台 | 32 | 300 × 50ms / 1000ms = 15 |
| ≤ 500 台 | 48 | 500 × 50ms / 1000ms = 25 |
| 1000 台 | **96–128** | 1000 × 50ms / 1000ms = 50，取 2 倍余量 |

⚠️ **但先改 `todayOutputOf` 的查库与锁，再谈加线程** ——
加线程只解决 L1，解决不了 L2（而 L2 的余量更薄）。

## 七、这个压测**测不到**什么（诚实清单）

1. **真实 PLC 的网络抖动与重传** —— L1 的 I/O 延迟是固定值/人工抖动，没有真实的丢包重传分布。
2. **JPA 实体装配与事务开销** —— L2 用 JDBC，真实值 **≥** L2 的值 ⇒ L2 的结论是乐观下界。
3. **Hikari 的连接借用/归还开销** —— L2 模拟了池的借用与归还语义，但没用真的 Hikari。
4. **WS 广播的真实成本** —— L1 没有客户端连接 ⇒ `broadcast` 走的是 `sessions.isEmpty()` 的早返回分支。
5. **其它定时任务的相互影响**（`EnergyRollup` 每秒扫全量、`AlarmEngine` 每 2 秒、`ErpProdInboundService` 每 10 秒）
   —— 它们与采集共享同一把 `ProdRollup` monitor，**本轮未量化其占比**。
6. **GC 压力下的表现** —— 堆增长在 120 秒窗口内未稳定，可能掩盖长跑后的 GC 停顿。
7. **多实例部署** —— 本轮是单进程。

## 八、护栏（防「压测绿了但什么都没验」）

| # | 护栏 | 怎么验的 |
|---|---|---|
| 1 | **calls : reads ≈ 1.0** | 断言比值 < 0.98 即红 |
| 2 | **负向对照 S6 必须变红** | 常量值驱动 ⇒ 路径没走到 ⇒ 必须红（`--expect-fail`） |
| 3 | **线程数必须在 shutdown 之前数** | 关掉池之后数只会得到 0，而「0 ≤ 池大小」恒成立 ⇒ 假绿 |
| 4 | **逐台判定，不许加总** | 「加总 > 0」会掩盖个别设备饿死 ⇒ 公平性测试逐台断言轮数 |
| 5 | **公平性护栏有变异验证** | 注入「部分设备首次执行推迟 500 倍」⇒ 测试红且诊断指对（「有 3 台设备一轮都没被采集到」）⇒ 还原后绿 |
| 6 | **编译失败必须硬校验** | 脚本曾把 mvn 输出管进 grep 再取 `$?` ⇒ **管道退出码是 grep 的** ⇒ 5 个场景全部 `ClassNotFound` 而汇总只说「未通过」 |
| 7 | **CPU 读不到就说读不到** | 反射调 `getProcessCpuTime` 被 JDK 模块系统拦 ⇒ 读到 -1，不能当成 0% |
