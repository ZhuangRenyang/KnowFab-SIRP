# Spec — DH-86 断线电量按时间摊回需量窗口

- **Status**: Draft → 实现中（2026-11-06）
- **Related**: ADR-001（P2）、DH-17（需量口径）、DH-81（计数器水位）、DH-80（库存口径）
- **前置结论**: **本 Spec 修正 ADR-001 里 P2 的实现方案。** 见 §2。

---

## 1. 目标与范围

### 问题（用代码事实描述）

工厂断网时，需量会**少算**——但原因不是「漏采了瞬时峰值」。

实际链路：

1. 采集层读的是电表的**累计电量**寄存器（不是瞬时功率），两次读数相减得到增量
   （`EnergyAccumulator.feed`）
2. 设备离线后恢复，一次读数就跨过了整段离线时间，差值里包含这段时间的全部电量
   —— **总电量不丢**
3. 但 `gap > 5 分钟` 时这笔增量被标 `backfill=true`
   （`EnergyAccumulator.BACKFILL_GAP_MS`）
4. `DemandTracker.feed()` 收到 `backfill=true` **直接 return，整段丢弃**

结果是**同一段电量在两处的口径不一致**：

| 口径 | 断网电量 | 位置 |
|---|---|---|
| 小时电量统计 | **计入**（`b.kwh += d.kwh()` 无条件） | `EnergyRollup:153` |
| 需量窗口 | **丢弃** | `DemandTracker:64` |

丢弃的初衷是对的（不能把 2 小时的电量塞进 1 个 15 分钟窗口，峰值会翻 8 倍，
客户会照着假峰值去申请扩容）。但代价是：

- 如果断网时段恰好是当月用电高峰，那个峰值**在需量里完全不存在**
- ⇒ 月度最大需量被低估 ⇒ 基本电费少算、**超容告警不触发**
- ⇒ 客户被供电局按实际峰值加收，而我们没提醒过他

### 范围内

1. **把断线电量按时间摊回它真正发生的那些 15 分钟窗口**
   —— 用已知的「起止时刻 + 总电量」，按与各窗口的时间重叠比例分配
2. `demand_window` 加 `estimated` 列，标记「这个窗口含推算值」
3. 需量页给一句**诚实提示**：哪些窗口是推算的、有多少电量没计入、峰值可能偏高还是偏低
4. 单测覆盖摊平的四个边界（比例、守恒、跨度上限、不覆盖真实数据）

### 范围外（明确不做）

| 不做 | 原因 |
|---|---|
| **边缘设备 / 本地缓存 / 断网续传** | 见 §2：我们采的是累计量，**本来就不丢总量**，不需要缓存层。加边缘组件是为了一个不存在的问题 |
| 采瞬时功率做需量 | 需量的定义就是 15 分钟平均功率，用累计电量差算才对。采瞬时点会在采样间隔里漏掉峰谷，还会被点表配错（`EnergyAccumulator` 类注释第 3 条） |
| 断网期间的负荷曲线插值 | 只有总量和时长，没有任何分布信息。任何「曲线」都是编的 |
| 摊平值回填到能耗小时表 | 小时表已经包含这段电量（`backfillKwh`），再回填就是双计 |
| 补采历史（重读设备的历史记录块） | 需要设备支持（DL/T645 冻结数据、Modbus 历史区），各家不一样。等客户提 |

## 2. 与 ADR-001 的偏差（**要改 ADR**）

ADR-001 的 P2 写的是：

> 需量瞬时的边缘缓存：累计量（产量/能耗）断网不丢（读设备累计计数器，差值自动补）；
> 只有**瞬时峰值**会漏，而需量按峰值计费 → 真的会算错钱

查代码后，这句话有两个地方不成立：

1. **「需量按瞬时峰值计费」——不是。** 需量是 15 分钟**平均**功率，我们一直用累计电量差算
   （`DemandTracker` 类注释第 1 条就写了「电费单上的最大需量是当月所有 15 分钟窗口里最大的那个平均功率」）
2. **「只有瞬时峰值会漏」——反了。** 漏的不是某个采样点，是**整段离线时间的电量被主动丢弃**

所以 ADR 里的「边缘缓存」是个**基于错误前提的方案**。加一个边缘采集器，采的仍然是
累计电量，`backfill` 判定照样会发生——问题一点没解决，只是多了一个组件要维护。

**正确的方案是纯服务端的**：把已经拿到手的电量按时间摊回去。零新增组件。

ADR-001 §四里「不做通用边缘计算平台」这一条**保持不变，而且理由更充分了**。

## 3. 关键裁决

### 3.1 摊平而不是丢弃，因为「不摊」的误差方向更危险

| 方案 | 峰值会偏高还是偏低 | 后果 |
|---|---|---|
| 全丢（现状） | **偏低**（该段为 0，可能整月峰值都丢掉） | 少算电费、**超容告警不响** → 客户被电网罚，我们没提醒 |
| 全塞一个窗口 | **偏高 8 倍**（2 小时塞进 15 分钟） | 客户照假峰值去申请扩容，白花几十万 |
| **按时间摊平** | 略偏低（均匀摊平会把峰值拉平） | 方向安全，且不会凭空造出峰值 |

摊平的误差是**已知且可解释的**：它给出的是「这段时间的平均功率」，不是真实峰值。
真实峰值只有补采到分布才能知道（范围外）。所以必须标记 + 提示（§3.3）。

### 3.2 摊平有上限：超过 **4 小时**就丢弃

设备离线 2 小时，摊到 8 个窗口，每窗口是这段的平均功率 —— 可接受。
设备离线 3 天，摊到 288 个窗口，每个窗口都填同一个平均值 —— **这不是数据，是伪造**：
它会让「本月最大需量」等于「月平均负荷」，客户拿着这个数去对账必然对不上。

所以：**跨度 ≤ 4 小时摊平，> 4 小时丢弃并记日志**。

选 4 小时的理由：工厂负荷在一个班次内的波动通常不超过 30%，4 小时摊平的峰值误差
在个位数百分比；再长就进入「换班 / 开关机」的量级，摊平开始失真。

> 阈值写死在代码里（`MAX_SPREAD_MS`），不做配置。理由同 ADR：不为一条边角功能
> 做通用平台。客户真需要更长，先看他的采集为什么断这么久。

### 3.3 推算值必须能被认出来，否则等于造假

`demand_window.estimated = 1` 表示该窗口含摊平电量。

为什么必须落库而不是只存内存：客户月底拿报表跟供电局对账时，要能分清
「这个数是电表实测的」和「这个数是我们推算的」。只在内存里标，重启就没了 ——
那就变成**无从追溯的假数据**。

前端**不给推算窗口换颜色**（图上花花绿绿反而看不清），只在文字里说明有 N 个窗口是推算的。

### 3.4 摊平不覆盖已有数据，只累加

`live.merge(key, share, sum)`，与现有逻辑一致。理由：同一窗口可能有别的点位的真实贡献
（一台设备挂了总表 + 分表，或两台表各算各的）。摊平只负责补上「这个点位在这一段该有的份额」。

**电量守恒**是硬要求：摊平后各窗口份额之和 == 原 delta（浮点误差 < 1e-6）。
这条要写成单测。

### 3.5 摊平不改变「网关重启后继承基线」的语义

`flush()` 里 `windowBaseline()` 的存在是为了重启后不冲掉已落库的量（DH-17 的坑）。
摊平走同一个 `addTo()` 入口，自然会先继承基线再累加，不需要额外处理。

### 3.6 `feed` 的签名要带上「从什么时候到什么时候」

现在只有 `ts`（读数时刻），摊平需要知道这段电量的**起点**。
`EnergyAccumulator` 内部有 `lastTs`，但没往外传 —— 加 `fromTs` 到 `Delta` 记录里即可，
不影响已有调用方（只有 `EnergyRollup` 一个）。

## 5. 接口变更

### 5.1 `DemandTracker.feed`（内部接口）

```java
// 旧
public void feed(String deviceCode, long ts, double kwh, boolean backfill)

// 新
public void feed(String deviceCode, long fromTs, long toTs, double kwh, boolean backfill)
```

- `backfill == false`：全部记入 `toTs` 所在窗口，`estimated = false`
- `backfill == true`：
  - `span = toTs - fromTs`
  - `span <= 0` 或 `span > 4h` → 丢弃 + `log.warn`（带设备、跨度、电量）
  - 否则按 `[fromTs, toTs)` 与每个窗口的重叠比例摊平，`estimated = true`

### 5.2 `GET /api/energy/demand/overview`（响应加字段）

```jsonc
{
  "dataQuality": {
    "estimatedWindows": 12,      // 本月有多少窗口含推算值
    "estimatedKwh": 340.5,       // 摊平进来的总电量
    "droppedKwh": 1200.0,        // 因跨度超限被丢弃、**未**计入需量的电量
    "hasGap": true               // = droppedKwh > 0，前端据此显示「峰值可能偏低」
  }
}
```

**`droppedKwh` 为什么不算准**：要精确知道「因跨度超限而丢弃了多少度」，得给每次丢弃落一条记录
（等于新建一张表）。`EnergyRecord.backfillKwh` 也不能直接用——它包含**已摊平**的那部分。

为一句提示加一张表不值得。所以只报**能准确算出来的**两项：
`estimatedWindows`（查 `estimated=1` 的行数）和 `backfillKwh`（`energy_record` 本月断线补偿总量）。

前端文案（不精确到「丢弃了多少度」，但不说假话）：

> 本月有 X 度电是断线后补读的：短时断线已按时间摊回对应窗口（标为推算）；
> 超过 4 小时的离线未计入需量，实际峰值可能更高。

```jsonc
"dataQuality": {
  "estimatedWindows": 12,     // 含推算值的窗口数（查 demand_window.estimated=1）
  "backfillKwh": 1540.5,      // 本月断线补偿总电量（查 energy_record.backfill_kwh）
  "hasGap": true              // = backfillKwh > 0
}
```

## 6. 验收标准（EARS）

- **AC-01** 当 `backfill=false`，系统应把电量全部记入读数时刻所在窗口，且 `estimated=0`
- **AC-02** 当 `backfill=true` 且跨度 40 分钟、电量 40 kWh，系统应按时间比例摊到 3 个窗口
  （份额 15/15/10 kWh，因首次进入的窗口从边界开始），**总和等于 40**
- **AC-03** 当 `backfill=true` 且跨度 > 4 小时，系统应丢弃该段并记 `WARN` 日志
  （含设备、跨度分钟、电量），且不产生任何窗口行
- **AC-04** 当某窗口已有实测值 10 kWh，再摊入 5 kWh，系统应得到 15 kWh
  且 `estimated=1`（说明这个窗口混了推算值）
- **AC-05** 当服务重启后继续摊平同一窗口，系统应先继承 `windowBaseline` 再累加，
  不得把已落库的值冲掉（DH-17 的回归）
- **AC-06** `overview` 在存在 `estimated=1` 的窗口时，`dataQuality.hasGap=true` 且
  `estimatedWindows` 与实际行数一致
- **AC-07** 摊平不得改变小时电量的统计（`EnergyRollup` 的 `b.kwh` / `b.backfillKwh` 保持原值）
- **AC-08** 单测：摊平各份额之和 == 原电量（浮点误差 < 1e-6）
