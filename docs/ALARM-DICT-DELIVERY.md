# 报警码字典扩品牌 · 交付说明

> 2026-11-05 | 范围：安川 / 松下 / 汇川 三个品牌补内置报警码表 + 修通台达 14 条「从未生效」的码

## 一、用户拿到什么

设备表单「伺服/PLC 品牌」下拉里，**原本「可选但无内置表」的三个品牌现在有表了**：

| 品牌 | 原来 | 现在 |
|---|---|---|
| 安川伺服 | 显示原始码 + 「未收录，查品牌手册」 | 按安川 Σ-7 / Σ-5 手册收录，维修工直接看到含义、原因、处理方法 |
| 松下伺服 | 同上 | 按 MINAS A6 / A5 手册收录（**新增「松下 A4 老款」独立选项**） |
| 汇川伺服 | 同上 | 按 SV660 / IS3 / IS5 手册收录 |
| 台达伺服 | 字典写了 14 条，但**生产中一条都命中不了** | **已修通**；并按官方手册补齐到 30 条 |

**每条码还登记了 2~3 种「现场可能写的别名写法」**（如安川 `A.720` 的 `1824` 与 `720` 都能查到）。

各品牌的**准确条数与来源**见 `src/main/resources/alarmcode-manifest.json`
（校验器会核对 manifest 与字典文件是否一致，改了字典忘了改 manifest 会被门禁拦下）。

维修工在大屏/维修卡上看到的是**厂家原始码**（`A.720`、`Err11.0`、`E410.0`），不是裸数字——
照着面板显示的码翻手册就行。

## 二、顺手修掉的一个存量缺陷（这个比扩品牌本身更值钱）

**台达 14 条报警码字典写了一年多，从来没生效过。**

- 字典键是三位补零（`001`），而设备上报的是裸整数（`1`）→ 归一化后不相等 → **0/14 可达**
- 表现：现场选「台达伺服」，报警码永远显示「未收录，查品牌手册」
- 修法：加载器加「去前导零别名索引」——**键形态一个字没改**（仍是三位补零），
  但运行时送裸整数（14、30…）能命中了。**原有 14 条全部可达**，
  同日按官方手册补齐的 16 条同样生效。
- **三菱零影响**（回归断言已钉住：19 个数值码行为不变，`8A` 仍是文档码）
- **历史维修单不断链**：`Resolved.code()` 恒等于 `normalize(rawCode)`，与字典键无关 → 历史 `alarm_code` 形态不变

> 换句话说：**台达用户此前一直看到「未收录，查手册」，升级后能直接看到含义了。**
> 字典本身没动一个字，变的是加载器认得它了。

## 三、本轮还订正了 8 条「含义与官方手册不符」的码

字典的错误含义比字典的缺失更危险：

- **查不到** → 现场看到「未收录，查品牌手册」→ 维修工去翻手册 → **安全**
- **查错** → 现场看到一条**看起来很权威**的错误含义 → 照错方向排查 → **危险**

本轮据**厂商官方手册**逐条核对，发现并订正了 8 条：

| 品牌 | 码 | 原含义（错） | 订正为（官方） |
|---|---|---|---|
| 台达 | AL008 | 位置控制误差过大 | 异常脉冲控制指令 |
| 台达 | AL009 | 通讯异常 | 位置控制误差过大 |
| 台达 | AL012 | 编码器通讯异常 | 校正异常 |
| 台达 | AL013 | 编码器数据异常 | 紧急停止 |
| 台达 | AL015 | 驱动器过热 | 正向极限异常 |
| 台达 | AL028 | 强制报警写入 | 编码器内部错误 |
| 三菱 | AL.11 | 控制电源异常 | 开关设定异常 |
| 台达 | AL029 | 格雷码错误 | 编码器内部地址错误 |

> 举例说明危害：三菱 AL.11 原写「控制电源异常」，维修工会去查 24V 电源；
> 官方实为「开关设定异常」，要查**轴编号/站编号参数设置**——排查方向完全相反。

**同日还按官方手册补齐了台达 16 条**（原 14 → 30 条）：
AL004 / AL014 / AL016 / AL018 / AL019 / AL020 / AL022 / AL023 / AL024 / AL025 /
AL026 / AL027 / AL029 / AL030 / AL031 / AL035，
其中 **AL014 反向极限异常**、**AL030 电机碰撞错误**、**AL022 主回路电源缺相** 是现场高频。

**核对来源**（均为官方手册逐页镜像）：
台达《ASDA-B2 用户手册》DELTA_IA-ASD_ASDA-B2_UM_SC_20201012.pdf 第 9 章《异警排除》；
三菱《MELSERVO-J4 伺服放大器技术资料集（故障排除篇）》§1.2 / §1.4。

## 四、两个容易被误解的地方（现场必须知道）

### 1. 三家的报警码数值口径不一样

| 品牌 | 面板显示 | 现场可能写进 PLC 的值 |
|---|---|---|
| 安川 | `A.720` | `1824`（驱动器寄存器原值 0x720）**或** `720`（照面板抄） |
| 松下 A6 | `Err11.0` | `11`（主码，子码合并进一条说明） |
| 汇川 | `E410.0` | `1040`（寄存器值 0x410）**或** `410`（照手册「故障代码」列抄） |

**两种写法系统都收**（每条码登记了主键 + 别名），现场怎么接线都能查到。
我做了全量验证：**每条码的每种写法都命中自己，0 异常**。

### 2. 松下 A4 必须单独选品牌

A4 的报警码是**两位**（Err 11），A6 是**主码**（Err 11.0）。
数字 11 在两代机器里含义相近但不完全相同，混在一张表里会让 A6 设备报「11」时命中 A4 的说法。
**A6 机器选「松下伺服（MINAS A6 / A5）」，A4 老机器选「松下伺服（MINAS A4 老款）」。**
（这是新加的下拉项，存量设备如果选了「松下伺服」但机器其实是 A4，需要改一次品牌。）

## 五、如实说明的已知限制

1. **「一个数字只对应一个含义」，同号多义的型号族用拆分品牌解决。**
   同一主码下有多个子码的（汇川 `E410.0` 主回路欠压 / `E410.1` 主回路断电），
   **合并成一条，处置方法并列写清**——不会给出一个与实际子码相反的排查方向。
   代价：维修工看到的是合并后的说明，具体是哪个子码要对照驱动器面板。

2. **仍有一类码查不到：数字撞车。**
   例：安川 `A.080`（光栅尺节距设定异常）的面板码 80，与 `A.050`（组合错误）的寄存器值
   `0x50`=80 撞上。**同一个数字不可能有两个含义**，所以 `A.080` 的面板写法不注册别名——
   现场若报 80 会命中 `A.050`。字典 `note` 里已写明这一点。
   **这类冲突只有 2 处**（已逐条实测），其余全部可查。

3. **PLC 自定义报警字仍然没有内置表**（这是设计如此，做不了）：
   那是设备厂程序里自定义的位，每台机器都不同。要用就按现场点表把位含义整理成字典文件。

4. **字符串型报警字暂不支持**：`resolve()` 只处理数值型点位。
   PLC 若用字符串报警字，需要另做一轮（键形态要重设）。

5. **汇川 AM 系列（AM600 多轴一体机）的 `AL-01~AL-35` 未收录**：
   适用型号尚未确认，且该系列用两位码，会与 SV660 的三位码空间混淆。宁可暂缺，不猜。

6. **三家的收录条数是「手册公开且语义明确的码」，不是全量翻译**：
   没收录的码显示原始值并提示查手册——**宁可少翻，不可翻错**。

7. **没有收录的其它品牌伺服（发那科 / 西门子 / 欧姆龙 / 雷赛等）仍需查手册**：
   本轮只做了「设备表单下拉里已有、但字典是空的」三个品牌（那是已承诺未兑现的缺口）。
   扩到新品牌要重新走一遍「官方手册核对 → 键制确认 → 语义核对」的流程，
   不能照搬本轮的键制（各家数值口径不同：安川是十六进制、汇川是十六进制、松下是主码级两位）。

8. **个别前缀码未收录（属「查不到来源」，不是遗漏）**：
   安川 `b.002` / `C.005` 这类前缀码、汇川 AM 系列 `AL-01~AL-35`，在官方资料中查不到对应码体系
   ⇒ 未收录，现场显示原始值并提示查手册 = **安全失败**（查不到，安全；查错才危险）。
   ⚠️ 容易误解的两点：**安川 Σ-5 的 `b.3x` / `b.6x` / `b.Fx`（b31/b32/b33/b6A/b6B/bF0~bF4）已收录且运行时可达**
   （数值身份 2865/2866/2867/2922/2923/3056~3060）；
   **汇川 `EA`/`EB`/`ED`/`EE` 族也已按官方 0x203F 取值建成数值主键**（如 EA41→2625、EE08→3592），
   运行时同样可达，并另以官方形态别名（`EA410`、`Er.A41`）保留人工查手册的入口。

## 六、质量门禁（本轮新建）

字典写错了以前没人会发现（不抛异常，只是「那个码永远查不到」）。本轮加了三道门禁：

| 门禁 | 位置 | 拦什么 |
|---|---|---|
| 静态校验 `scripts/check-alarmcodes.mjs` | `make-dist.sh` **构建之前** + `release.sh --no-build` 分支 | 键形态、归一化后唯一性、生产可达性、清单一致性、跨品牌冲突 |
| 字典单测 `AlarmCodeDictTest`（18 条） | `mvn test` | 存量行为逐条钉住 + 别名机制契约 |
| 黄金样本 `AlarmCodeGoldenTest` | `mvn test` | 手写语义断言，防「集体性错误」 |

**门禁本身做了反向验证**：故意制造补零键、含字母键、删清单行、加空格、清空字段、
制造归一化碰撞、两文件同品牌 —— **11 类变异全部被精准拦住**，还原后恢复原状。

> ⚠️ 注意：发版流程内部是 `mvn -DskipTests clean package`，**JUnit 在打包时不跑**。
> 所以静态校验器特意做成**零依赖 Node 脚本**并接在构建之前——
> **「写了测试」不等于「测试会被跑」，这是本项目反复栽过的坑。**
