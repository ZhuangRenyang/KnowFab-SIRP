# ADR-001：产品方向——从「四合一」收口到「设备直连的轻量 MES」，并用工作流给 AI 装上手脚

- **Status**: Accepted（2026-11-06）
- **Deciders**: 用户 + 项目总监
- **Related**: DH-85（工作流最小版）、DH-86（需量边缘缓存）、DH-84、ROADMAP A/B/C 段

---

## Background（为什么必须现在定）

2026-11-06 做了一次基于代码的盘点，结论与「ERP + MES + IoT + AI 四合一」这个说法有明显偏差：

| 层 | 体量 | 实际深度 |
|----|------|----------|
| ERP | 68 个类 | 库存（7 类单据）/采购/销售/往来/收付款/成本（料工费）/报表 |
| 质检 | 38 个类 | AQL 国标逐格照抄 + 检验/判定/处置/放行/退货/对账 |
| IoT | 17 个类 | Modbus TCP/RTU/RTU-over-TCP + OPC UA + 485 + 网段扫描 + 点表探测 |
| AI | 13 个类 | 12 个**只读**查询工具 + 诊断→工单→回填闭环 + 早报 |
| alarm/energy/report/demand | 14/13/13/9 | 各一条完整链路 |

全项目 243 个 Java 文件、36 个实体、40 个控制器。`1.0.28` 已在真机跑通七阶段安装（19 过 / 0 挂）。

**所以「范围太大、做不完」不是当前风险 —— 东西已经做完了，还没有一个客户在天天用。** 这两个风险的解法完全不同：前者砍范围，后者找人。继续扩功能只会让后者更难。

按 MESA 的 11 项 MES 能力对照，我们覆盖约 5-6 项（数据采集、质量、性能分析、工单、维护强；排程是产线粒度）。**缺的是「工序路线」**——一单只有一道活，不能车→铣→磨流转。ERP 侧没有总账/凭证/科目，是往来账不是财务会计。

真正卡住 AI 的不是模型，是**没有可被调用的动作层**：AI 现在只能输出一段文字建议，不能「建维修单、派给张三、通知班长」。这是与普通 MES 唯一的差异点，也是唯一值得现在补的功能。

## Decision

### 一、对外定位（销售口径，不是愿景）

> **设备数据直连的轻量 MES + 进销存**
> 产量不用人录，库存和单据永远对得上。

**不说**「AI Manufacturing OS」「四合一平台」。理由：叫 OS 会让客户期待平台能力（可被集成、开放 API、插件生态），而我们是单厂交付的成品软件，定位抬高会拉长销售周期。

对内愿景可以写「AI 原生制造运营系统」，这不冲突——但**对外只说前者**。

### 二、切口：按场景，不按行业

**不做**「专注注塑 / 五金 / 电气行业」。理由：按行业切会逼我们补那个行业的工艺知识（模次、保压曲线、热处理参数、安规），那是另一个战场，我们没有行业专家。

**改按场景切**：

> 「有几十台设备、老板要随时知道产量和库存对不对得上、但不想雇文员每天录数」的厂。

这个场景跨行业，且正好是我们的强项（设备计数自动生成生产入库单）。

### 三、开发优先级（本轮唯一的三件事）

| 优先级 | 事项 | 为什么是它 | 编号 |
|--------|------|-----------|------|
| **P0** | **收口交付**：A 段剩下 4 项（关演示数据 / 现场通信参数+断网演练 / 真实仓库地址 / 备份演练） | 功能已完整，装不上或没演练过等于白做。这一层不做完，卖出去就是事故 | DH-03/07/08/09 |
| **P1** | **工作流最小版**：审批 + 派工 + 通知 + 让 AI 能调用写操作 | 这是「AI 只能建议」的根因。补完 AI 才从「会说」变成「会办」，这是唯一的产品差异点 | **DH-85（新）** |
| **P2** | **断线电量摊回需量窗口**（原写「需量瞬时的边缘缓存」，**已修正**，见下） | 累计量断网不丢（读设备累计计数器，差值自动补），但需量**把补读回来的电量整段丢弃**了 → 断网若恰逢用电高峰，那个峰值在需量里完全不存在 → 月最大需量低估、**超容告警不响**。改成按时间摊回对应窗口，纯服务端，不需要任何边缘组件 | **DH-86（2026-11-06 已完成）** |

#### P2 方案修正（2026-11-06，动手前查代码发现）

原文写的是「只有**瞬时峰值**会漏，而需量按峰值计费」。查代码后两处不成立：

1. **需量不是按瞬时峰值计费**，是按 15 分钟**平均**功率。我们一直用累计电量差在算
   （`DemandTracker` 的类注释第 1 条写得很清楚），从来没采过瞬时功率点。
2. **漏的不是某个采样点，是整段离线时间的电量被主动丢弃**——
   `EnergyAccumulator` 把 `gap > 5 分钟` 的增量标成 `backfill`，`DemandTracker` 收到就 `return`。

所以「加一个边缘采集器做缓存」是个**基于错误前提的方案**：边缘端采的仍然是累计电量，
`backfill` 判定照样发生，问题一点没解决，只是多了一个组件要维护。

正确解法是纯服务端的：**把已经拿到手的电量按时间摊回去**（份额 = 电量 × 窗口内重叠时长 / 总跨度），
跨度超过 4 小时才丢弃（摊 3 天等于伪造数据）。零新增组件。
详见 `docs/SPEC-DH86-DEMAND-BACKFILL.md`。

> 这一条也顺带印证了 §四「不做通用边缘计算平台」——理由比原来更充分了：
> 不是「暂时不需要」，而是**这个问题根本不在边缘侧**。

### 四、明确不做（写死，防范围蔓延）

| 不做 | 原因 | 什么时候重新考虑 |
|------|------|------------------|
| 平台化 / 开放 API / 插件市场 | 单库单应用是护城河：数据天然关联、装完就能用、不需要实施顾问对接三套系统 | 有 10+ 客户且他们要求被集成时 |
| MQTT / 多厂 / 多租户 | 是另一个产品形态（SaaS），不是加个协议的事 | 明确要做 SaaS 时 |
| 财务总账 / 凭证 / 科目 | 会把项目拖成财务软件，ROI 低；客户有财务软件 | 客户明确要求，且愿为合规付钱 |
| 通用边缘计算平台 | 只有需量这一条真需要（见 P2） | 客户有断网刚需场景 |
| 预测性维护 | 没有足够的设备历史数据与故障样本，做了就是编数据 | 单客户积累满 1 年数据 |
| 工序路线（routing） | 是 MES 骨架，但**先看客户是否多工序**；做它要改工单模型 + 报工 + 排程 | 第一个客户确认是多工序装配 |
| 二次抽样 / 加严放宽自动转移 | 已在 OPEN-DECISIONS 登记，等客户明确要求 | 验厂被要求时 |

## Consequences

**正面**
- 功能不再扩面，交付与验证的精力集中到「能不能装、能不能用」上
- AI 从「查询层」升级为「动作层」，形成真正的差异化叙事
- 定位收窄后，销售话术一句话能说完，客户不需要理解四个缩写

**负面 / 要接受的代价**
- 「四合一平台」的故事讲不了，对投资人的吸引力下降
- 放弃「专注某个行业」意味着短期拿不到行业标杆案例
- 工作流最小版会引入新概念（流程定义、待办、通知渠道），有过度设计的风险 —— 所以限定「最小版」：只做审批 + 派工 + 通知三类动作，不做通用 BPMN

## 不做的事（对内的纪律）

- 本 ADR 定的是**产品方向**，不是技术架构。技术选型（Vue3 + Vite、Spring Boot、MySQL）继续按 Spec 走，不因本决策改动
- 本 ADR 的「不做清单」是**开发纪律**：任何人提这些需求，先回来看这一节，要改就得先改 ADR
- 本 ADR 不解决「找不到客户」的问题。找客户不是开发任务，但优先级高于本 ADR 里的 P1/P2
