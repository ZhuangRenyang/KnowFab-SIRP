## 1. 目标与范围

**一句话**：给安川 / 松下 / 汇川三个品牌补上内置报警码表，维修工在界面上看到的是**厂家原始码**（`A.720`、`Err11.0`）而不是光秃秃的数字；同时把台达那 14 条「从未生效」的码修通，并按官方手册补齐到 30 条。**最终规模：6 个字典文件 / 356 条码 / 586 个别名写法。**

### 范围内（P0）

| # | 功能 | 验收锚点 |
|---|---|---|
| 1 | 新增 3 个品牌字典文件（安川 / 松下 / 汇川），收录手册全量码 | 三个 brand 键可加载、可命中 |
| 2 | 字典条目新增 `displayCode`（厂家原始码）并透出到 API | `plcWords[].displayCode` 与手册逐字一致 |
| 3 | 大屏 / 维修卡优先显示 `displayCode` | 未收录的码显示不变（向后兼容） |
| 4 | 加载器加**去前导零别名索引** | 台达 14 条从「0 条可达」变「14 条可达」；并按官方手册补齐到 30 条 |
| 5 | 字典静态校验器接进发版门禁 | 写错字典键 = 发不出包 |
| 6 | 松下 A4 拆独立 brand 键 + 前端加选项 | A6 现场送主码时「查不到」而非「查错」 |
| 7 | 存量三菱 / 台达**行为逐字节不变** | 回归率 = 0 |

### 范围外（明确不做，防止蔓延）

- **不动数据库**：不加 `servo_model`、不写迁移、不做存量回填（§3.3）
- **不改 `normalize()`**：连带 `Err.11.0`→`R110`、`AL-011`→`-011` 两条副作用本轮不修（§9）
- **不改 `lookup()` 签名、不改 `Resolved.code()` 语义**（只**追加** `displayCode`）
- **不支持字符串型报警字**（`resolve()` 只处理 `Number`）—— 它不是独立的一件事：一旦支持，键形态必须重设（§9 坑 3）
- **不把「同号不同义」的型号族塞进同一 brand 键**：冲突的必须拆 brand 键（§3.2）
- **不引入新依赖 / 中间件 / ORM**：校验脚本用 Node 内置模块（沿用 `scripts/check-i18n.mjs` 约定，零新依赖）

## 2. 关键决策（7 个分歧已裁决）

### 2.1 裁决：字典键 = **数值身份**，命名空间机制不引入

- **分歧**：架构师主张「命名空间 + 主体」键（`A720`/`AL011`/`ER101`）+ `namespaces/digits/default` 三层元数据；项目总监主张「键 = 数值」。
- **裁决**：**采纳数值键**，撤回命名空间机制。
- **理由**：运行时只有一个数字通道 ⇒ 命名空间机制能把两条同号码都**存下**，但寄存器只送一个数字 ⇒ **第二条照样到不了** ⇒ 用 4 个元数据概念换 0 个可达性收益 = 过度设计。
- **Consequences**：+ 机制最小、存量零破坏；− 同号不同义的型号族必须拆 brand 键（§3.2）。

### 2.2 裁决：键的合法性判据 = **数值身份**，不是字面形态

> **「含字母」是手册的书写形态，不是码的数值身份。能否送达取决于数值身份，不取决于字面里有没有字母。**

- `A.7A1` = `0x7A1` = **1953**，是合法 16 位整数 ⇒ 寄存器送得上来 ⇒ **含字母主体码照收**。
- ⇒ **键 = 该码在「寄存器整数通道」上的数值身份**；其它写法（官方形态、手册裸数字）一律进 `aliases[]`（§5.3）。

### 2.3 裁决：`normalize()` **一行不改**（冻结）

- 改了会让存量品牌的 `Resolved.code()` 变形 ⇒ `erp_maint_order.alarm_code` 形态变化 ⇒ **维修单历史样本断链**。
- 它的实际服务面只有「人工输入」这条当前不存在的路径。
- ⇒ 连带：`Err.11.0`→`R110`、`AL-011`→`-011` 两条副作用本轮不修，写进 §10 已知限制。

### 2.4 裁决：两条 normalize 层红色断言**撤销**，意图由数据层门禁继承

- `noPrefixMustNotCollideWithBareCode`（`No.12`）→ **撤销**：五个品牌都没有 `NO.` 前缀家族，是假命题；撤销处留注释写明理由与重新成立的条件。
- `alPrefixAndErPrefixMustNotCollide`（`AL.01` vs `Er.01`）→ **撤销 normalize 层的表达**：在 normalize 层满足它必须改 `normalize()` ⇒ 与「不改 normalize」正面冲突。意图改由 **G1/G2/G5** 三条数据层门禁继承（§7.2）。

### 2.5 裁决：ADR-D —— **修台达**，实现方式 = 加载器去前导零别名索引

- **事实**：`Resolved.code()` 恒等于 `normalize(rawCode)`，**与字典 key 无关** ⇒ 历史 `alarm_code` 一直存的是 `"1".."28"` ⇒ **修台达不断历史样本链，零数据迁移**。
- **Decision**：**不动台达 JSON 文件**（存量 34 条 key 形态逐字节不变），改加载器。
- **Consequences**：+ 台达 14 条生效；+ 三菱零影响（`"8A"` 非数字，别名规则不适用，仍不可达）；− **diff 里看不到台达文件变化，但行为变了** ⇒ 必须写进变更记录（§12.3）。

### 2.6 裁决：数值身份**按品牌分别定规则**；每码登记**两种纯十进制写法**；**字母形态不入库**

- **分歧**：平铺多键 vs 主键 + 别名表 vs 只留一种写法。
- **裁决（经官方手册核实后定稿）**：
  1. **数值身份按品牌分别定规则**（各品牌的官方码制不同，**不能套一条统一规则**）：

     | 品牌 | 数值身份规则 | 官方依据 |
     |---|---|---|
     | 松下 | 去掉字母前缀与点后的数字串（**十进制**） | MINAS A6 Multi Technical Reference §7.1 |
     | 安川 | **十六进制码值转十进制** | 官方手册码带 `h` 后缀（`720h` = 0x720） |
     | 汇川 | **十六进制位值转十进制** | SV660N Communication Guide 的 Error Code(603Fh) / Aux. Code(203Fh) |

     > ⚠️ **安川不能用「去掉所有字母」**：安川码是十六进制，`A.7A0` 的数字段是 `"7A0"`（里面的 A 是十六进制数字位，不是前缀）⇒ 剥字母会把它变成 `70` ⇒ **15 组撞车**。必须按 16 进制解析 ⇒ `0x7A0` = 1952。
     > ⚠️ **汇川不能用「去掉所有字母」**：E 族主码三位（→4 位）与 EA/EB/ED/EE 族主码两位（→3 位）**数字空间交叠** ⇒ 实测 6 组跨族撞车（`111`、`200`、`030`、`031`、`050`、`090`）⇒ **必然有一条被静默丢弃** ⇒ 见 §3.1 的收窄口径。

  2. **每码登记两种纯十进制写法**（都可达、都是整数）：
     - **数值身份**（读驱动器寄存器拿到的值）：安川 `1824`、汇川 `1040`
     - **手册裸数字**（集成商按面板码字映射时写的值）：安川 `720`、汇川 `410`
     ⇒ **两种现场写法都命中，零约定成本** ⇒ 不必去确认现场惯例，把这个不确定性从产品里拿掉。
  3. **字母形态做 `aliases`，不做主键**：`"A720"` / `"R110"` / `"E4100"` / `"EB010"` ⇒ 寄存器是整数，装不下字母 ⇒ **运行时送不到** ⇒ 不做主键；但**保留在 `aliases[]` 里** —— 将来做字符串型报警字时**直接可用，不必重做数据**。
     ⇒ 顺带：安川 `A.7A1` 这类**主体含十六进制字母**的码，其数值身份是 `0x7A1` = **1953**（纯数字）⇒ **照收不误** ⇒ **判据是「数值身份」，不是「字面里有没有字母」**（§2.2）。
  4. **子码合并**：同一主码下的多个子码**合并成一条**（含义差异写进 `cause`），登记时只留**主码级**的那个数值身份。
     ⇒ 例：汇川 `E410.0`（主回路电欠压）与 `E410.1`（主回路断电）⇒ 官方对象取值两者都是 `0x0410` ⇒ **数值上不可区分** ⇒ 合并成一条，`displayCode` 写 `"E410.0 / E410.1"`，`cause` 分开写两态。
  5. **同主码不同义的型号族必须拆 brand 键**（§3.1、§3.2）。

### 2.7 裁决：松下 A4 拆独立 brand 键

- **理由**：A4（两位码 11..99）与 A6（三位码 110..9900）同处一个 brand 键 ⇒ **A6 主码与 A4 码有 30 个值相同** ⇒ 现场按「只送主码」的常见做法上报会**命中 A4 的含义**（如写 `41` 命中「绝对编码器计数出错」，实际应是 `Err41.x`）⇒ **这是查错，不是查不到**。
- **Decision**：`panasonic` = A6 + A5（286 条）；`panasonic-a4` = A4（39 条）。**前端必须同步加选项**（§6）。
- **拆后语义**：A6 现场送主码 `11` ⇒ `panasonic` 里没有 `"11"` ⇒ **查不到**（显示「未收录，查松下手册」）⇒ **宁可查不到，不可给错含义**。

### 2.8 裁决：松下展示形态 = `Err11.0`（**不是 `AL.001`**）

- **证据**：`AL030` 的说明写「达到 **P1-57** 的扭矩设定…**P1-58** 的设定时间」、`AL099` 写「执行 **P2-08**=30,28 后重新送电」—— `P1-57`/`P1-58`/`P2-08` 是**台达 ASDA** 的参数体系（松下是 `Pr5.04`/`Pr6.10`/`Pr0.16`）⇒ **`AL001`~`AL017` 是台达的码，不是松下的**。
- 松下官方《A6 家族关联报警&警告代码一览》Ver1.05 共 8 类 151 条，**一条 `AL.` 都没有**，全是 `Err11.0` 这种形态。
- ⇒ **`displayCode` 以官方手册为准**；任务书里「松下 `AL.001`」的前提**作废**（若照抄，维修工拿松下 A6 查表会被指错方向 —— A6 的过流是 `Err14.0`）。

## 3. 数据组织

### 3.1 brand 键 = 一个「数值空间互不冲突」的型号族

| brand 键 | 覆盖 | 键形态 | 键数 / 含义数 |
|---|---|---|---|
| `mitsubishi` | 三菱 MR-JE/J4 | 两位 + 一个字母码 | 20 键 / 20 含义（19 个数值身份） |
| `delta` | 台达 ASDA-B2/B3 | 三位补零 | 30 键 / 30 含义（按官方 §9.1 全表补齐） |
| `yaskawa` | 安川 Σ-5 / Σ-7 | 十六进制位值（主）+ 手册裸数字 / 官方形态（别名） | 117 主键 / 117 含义 |
| `panasonic` | 松下 MINAS A6 家族 + A5 | 主码级两位（主）+ 别名 | 55 主键 / 55 含义 |
| `panasonic-a4` | 松下 MINAS A4（MHMF） | 两位（主）+ 别名 | 39 主键 / 39 含义 |
| `huichuan` | 汇川 E 族 + EA/EB/ED/EE 族 + IS3/IS5/IS600/SV 老平台 | 十六进制位值（主）+ 手册裸数字 / 官方形态（别名） | 95 主键 / 95 含义（覆盖 271 个厂家码） |

⚠️ **松下 `panasonic` 与 `panasonic-a4` 的数字空间完全重叠（都是两位）** ⇒ 两者靠 **brand 键**区分 ⇒ 现场设备必须选对品牌 ⇒ 这正是 §2.3「跨族同号不同义 → 拆 brand 键」的落地形态（拆了有效：选表就选对了）。

⇒ **汇川的 aux 族（EA/EB/ED/EE）已全部收进 `huichuan`** —— 依据官方《SV660N Communication Guide》的 Aux. Code(203Fh) 列逐条验证（`EA33`→`0x0A33`=2611、`EE08`→`0x0E08`=3592、`EB03`→`0x0B03`=2819、`ED09`→`0x0D09`=3337 …）⇒ **用官方十六进制位值作数值身份后，跨族数字空间不再交叠**（E 族 `0x` 区间 256..2452，aux 族 0..65）⇒ **不需要拆 `huichuan-aux`** ✓ ⇒ 含整组 EtherCAT/PN 总线报警（EE08~EE20），是汇川现场最常见的总线类故障。

⇒ **汇川数值身份的统一规则（已用官方原表与全表自洽性双重验证，89/89 一致、0 例外）**：
> **数值身份 = `0x0` + 三位主码**（官方手册原表逐行验证：`EA41.0 → Error Code(603Fh) = 0x0A41`、`Aux. Code(203Fh) = 0x0A41` ⇒ `0x0A41` = **2625**）。
> - E 族：三位主码是纯数字 ⇒ `E410.0` → `0x0` + `410` = `0x0410` = **1040**
> - aux 族：三位主码含族字母 ⇒ `EA41.0` → `0x0` + `A41` = `0x0A41` = **2625**；`EB01.0` → `0x0B01` = 2817；`EE08.0` → `0x0E08` = 3592；`ED09.0` → `0x0D09` = 3337
> ⇒ **字母族标记（E/A/B/D）只存在于「显示形态」，不进数值身份** ⇒ **把字母族当高位标记（`EA41` → `0xEA41` = 59969）在官方手册里查不到该值，不成立**。
> ⇒ **判据一句话**：**E 族 `E410` = `0x0410` 而非 `0xE410`，已经证明字母不进数值身份** ⇒ aux 族同理。

⚠️ **`Er.D03`（CAN 通信连接中断）移出 `codes` 写进 `note`** —— 它的寄存器数值身份在官方资料里查不到 ⇒ 不能凭空给键。

### 3.2 跨族同号不同义 → **拆 brand 键**；同族内子码不同义 → **合并成一条**

| 情况 | 处理 |
|---|---|
| 同一编号，含义实质相同（仅前缀不同：故障 E / 告警 A） | 合并为一条，`cause`/`remedy` 写通用处置 |
| 同一编号，子码不同但主因相同（如 `E201.0/1/2/4` = P/U/V/N 相过流） | 合并为一条，**`cause` 必须逐条列出子码含义** |
| 同一编号，**跨族**主因不同 | **拆 brand 键**（拆了有效：选表就选对了） |
| 同一编号，**同族内子码**主因不同（如 `E410.0` 欠压 / `E410.1` 断电） | **合并成一条**（拆了无效：寄存器值都是 410，运行时选不出来） |

> **一句话原则**：拆 brand 键只能解决「跨族同号不同义」；解决不了「同族内子码不同义」。

### 3.3 型号与总线维度：**不加 schema 字段**，用扩展 brand 键承载

- 会改变同号含义、却无法在运行时选中的属性（型号、总线），统一用**扩展 brand 键**表达，不再开 `series[]` / `bus[]` / `severity` 维度（否则键空间按二维爆炸，而运行时仍只有一个数字通道）。
- 扩展键不进前端下拉时，现场改库值即可：`UPDATE device SET servo_brand='panasonic-a4' WHERE code='<设备码>';`（`servo_brand` 是 `varchar(24)`，长度足够）。

## 4. 数据契约：字典 JSON schema（锁定）

```json
{
  "brand": "yaskawa",
  "brandText": "安川伺服（Σ-5 / Σ-7 系列）",
  "note": "来源：Yaskawa Σ-7 手册 6.1 List of Alarms + Σ-5 报警表。键=十六进制码值的十进制；displayCode=厂家原始形态；aliases=其它可接受写法。",
  "codes": {
    "1824": { "displayCode": "A.720", "name": "过载（连续最大负载）",
              "cause": "...", "remedy": "...",
              "aliases": ["A720", "720"] }
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `brand` | string | 是 | 品牌键，与 `device.servo_brand` 同值域；**全库唯一**（G3） |
| `brandText` | string | 是 | 界面显示名 |
| `note` | string | 是 | 来源手册 + 收录范围 + 已知限制 + 型号错配怎么办 + **未收录码的留空约定** |
| `codes` | object | 是 | 数值身份 → 条目；非空 |
| └ **键** | string | 是 | **纯数字**，= 该码的**数值身份**（官方对象取值；汇川与安川为十六进制位值，松下为主码级十进制）。**主键每条含义只有一个** |
| └ `displayCode` | string | 是 | **厂家原始码/手册形态**，逐字抄手册，不许规范化；多子码合并时列出全部子码 |
| └ `name` | string | 是（非空） | 报警名称；**同号多形态时须写明各形态差异** |
| └ `cause` | string | 是（非空） | 可能原因；**多子码合并时须逐条列出子码含义** |
| └ `remedy` | string | 是（非空） | 处理办法；不许写「检查设备」这类空话 |
| └ `aliases` | array of string | 选填 | **同一含义的其它写法**：厂家原始形态（`A720`/`R110`/`E4100`/`AL001`）+ 手册裸数字。**不得与任何主键或已注册别名冲突**（G5/G7/G8/G9）。⚠️ **数字段别名一律不给**（如汇川 `EA41` 的数字段 `"41"`）⇒ 因为它跨型号族重号（`EA41`=2625 与 `E041`=65 都是「41」），给了就会把一个含义挂到别的数字上 ⇒ **宁可少一种写法，不可给错含义** |

**存量文件**（`mitsubishi-servo.json` / `delta-servo.json`）：`key` / `name` / `cause` / `remedy` 一律不动；`displayCode` 与 `aliases` 是否补，见 §12.3 的裁定记录。

## 4.5 数据撰写约定（扩任何品牌都照它办）

**① 手册表的「名称列」≠「详细名称」—— `name` 必须取名称列**
- 手册结构常是「**名称** | **详细编号** | **详细名称**」三列（例：三菱 MR-J4 §1.2，报警号 `24` 的名称列 = 「主电路异常」，`24.1`/`24.2` 的详细名称 = 「伺服电机输出接地故障」）。
- ⇒ **`name` = 名称列**（那是驱动器面板上的主标题）；**详细项写进 `cause`**（例：`cause` = 「伺服电机输出端 U/V/W 相接地故障（AL.24.1 硬件检出 / AL.24.2 软件检出）」）。
- ⇒ **把详细名称当名称写进 `name`，等于把官方手册里正确的名称改错** —— 现场一对照就对不上，反而更困惑。
- ⇒ **同一官方名称对应多个中文细分时**（例：台达 `AL025`~`AL029` 五条官方名称完全相同，都是 The Internal of the Encoder is in Error）⇒ **不能靠 `name` 区分，细分必须落到 `cause`**。
- ⇒ **易混的邻近码要在 `note` 里点名**（例：台达 `AL030` = Motor Crash Error 电机碰撞错误，与 `AL025`~`AL029` 的编码器类名称相近，最易写混）。

**② 收录前先花十分钟把官方表头看明白 —— 列结构比逐条抄更值钱**
- 找到列结构（名称列 / 详细编号列 / 详细名称列；Error Code 列 / Aux. Code 列），**一次就能定一整族的键制与写法规则**。
- 实例：三菱 §1.2 的三列结构 ⇒ 一眼定出「`name` 放名称列、详细说明放 `cause`」；汇川的 Error Code / Aux. Code 两列 ⇒ 一眼定出「**数值身份 = `0x0` + 三位主码**」⇒ **89 条一次性自洽**。
- ⇒ **比逐条抄 300 条省事，也比逐条抄更不容易错。**

**③ 每条内容订正都要钉进语义清单**
- ⇒ 订正完不改清单 = 下次有人改回去没有测试会红 ⇒ ⇒ **订正条目 + 新补的码，都要进语义清单**。

## 7. 机械门禁

### 7.1 接入点

| 门禁 | 位置 | 验什么 |
|---|---|---|
| **静态** | `tools/make-dist.sh`（**构建步骤之前**） | 数据写对没：键形态、唯一性、可达性、条数对账 |
| **行为** | `tools/qc-gate.py`（起服务后） | 修完真的生效没：台达命中数、三菱回归率、新品牌代表码、`displayCode` 一致性 |

> 静态校验必须放在**构建之前**：构建之后的话，错的字典已经把 jar 编出来了，`tools/release.sh --no-build` 快速重发会直接把它打进去 ⇒ 门禁反而漏了。

### 7.2 门禁清单（`scripts/check-alarmcodes.mjs`）

| # | 断言 | 判定 |
|---|---|---|
| V1 | index.txt 清单 ↔ 实际 json 文件**双向**一一对应 | 阻断 |
| V2 | schema 完整；`name`/`cause`/`remedy`/`note`/`displayCode` 非空 | 阻断 |
| V3 | 字典的 brand 键必须在前端 `BRANDS` 里（扩展键 `<主键>-<型号>` 放行但提示） | 阻断 / 提示 |
| V4 | 同品牌内 key 归一化后唯一（G1） | 阻断 |
| V4b | 同品牌内**去前导零后**唯一（G2） | 阻断 |
| V4c | **不同文件的 brand 不得相同**（G3） | 阻断 |
| V5 | 生产可达性：键必须是可送达的数值身份 | 阻断 |
| V6 | key 无前后空格 | 阻断 |
| V7 | manifest 对账：**`expectedCount` == 文件实际键数**（脚本机械断言）；`numericIdentityCount` = 数值身份数（人工对账用，脚本不判）；`displayFormKeyCount` = 展示形态键数 | 阻断 |
| **G5** | 带前导零的键，其去零形态不得是本品牌已有键；**别名不得覆盖已有键** | 阻断 |
| **G5** | 别名不得覆盖任何主键 | 阻断 |
| **G6** | **前端 `BRANDS` 里的每个品牌，字典里必须有同名 brand 键** | 阻断 |
| **G7** | `aliases[]` 合法：必须是数组、元素非空、不得覆盖任何主键 | 阻断 |
| **G8** | **别名之间也必须唯一**（一个别名只能指向一个含义） | 阻断 |
| **G9** | **别名必须真的指向它自己**（防止把 A 的含义挂到 B 的键上） | 阻断 |
| **V8** | manifest 对账：文件实际条数 == `expectedCount`，且四个数（键数 / 数值身份数 / 含义数 / 别名数）互相自洽 | 阻断 |
| **selfTest** | 校验器**自检**：脚本自己跑一遍内置的"故意错"样例，断言每一种错都被抓到 | 阻断（自检失败直接 exit 1） |

- **V3 与 G6 合起来才是双向覆盖**：V3 正向（字典→前端），G6 反向（前端→字典）⇒ 「brand 写成 `yaskawa-sigma7`」这类静默失效被 G6 直接拦下。
- **G8 与 G9 是两道不同的闸**：G8 管「一个别名只能被一条含义占用」，G9 管「别名必须指向它自己」⇒ ⇒ **「别名把 A 的含义挂到 B 的键上」这类错含义，必须两条同时在**。
- **selfTest 是门禁的门禁**：「脚本被改残 ⇒ 检查项失效 ⇒ 什么错都拦不住」这种失效不会抛异常、只会静默放行 ⇒ ⇒ 用一个内置的"故意错"样例在每次运行时自检，任何一条检查被改残 ⇒ 自检先失败 ⇒ ⇒ **（本项目已栽过两次同类坑：`-DskipTests` 跳过 JUnit、校验器忘了调 `main()`）**。
- **存量豁免**：只豁免**具体的键形态**（如台达的补零键、三菱的 `8A` 字母码），不豁免整个文件 ⇒ 豁免项必须写成可机器判定的规则，否则将来给台达补一条新的补零码会被漏放。
- **豁免的是「形态检查」，不是「可达性检查」** ⇒ 台达修完后，补零键已可达，但仍要保留形态标记（否则后人以为台达键就该补零）。

### 7.2b 变异验证（可复跑脚本）

`scripts/mutation-check-alarmcodes.mjs` —— 把字典与 manifest 拷到临时目录 → 注入一个错误 → 跑校验器 → **断言必须 exit 1**。
⇒ **不碰真文件**（校验器支持 `ALARM_DIR` / `ALARM_MANIFEST` 环境变量覆盖）⇒ ⇒ **判据是「注入错误 → 必须 exit 1」，不是「跑一下 exit 0」**。
⇒ **当前 11 类变异全部被拦住**：① 清单行被删 ② 键前后加空格 ③ `remedy` 被清空 ④ 归一化碰撞 ⑤ 两文件同 brand ⑥ 新品牌出现补零键 ⑦ 新品牌出现含字母键 ⑧ `displayCode` 被清空 ⑨ 别名覆盖另一个主键 ⑩ **别名 = 另一个条目的别名** ⑪ manifest 条数与字典对不上。

### 7.3 基线快照（自动生成）

`src/main/resources/alarmcode-golden.txt` —— 由脚本导出**每个主键 + 每个别名**各一行（共 **943 行** = 356 主键 + 586 别名），格式 `品牌 | 键 | 期望命中 | 期望含义 | 备注`。
⇒ **主键全量**：内容漂移必被 diff 出来；⇒ **别名全量**：别名被误删/误加也会被 diff（这是最容易漏的 —— 别名不在 `codes` 里，只看主键快照看不见）。
⇒ 备注用 `·` 不用 `|`，避免解析器把备注里的分隔符当字段。

### 7.4 行为断言清单（手写，只钉不变量）

`src/test/resources/alarmcode-golden-semantic.txt`（品牌 | 运行时输入 | 期望命中 | 期望含义）

**设计纪律（这条是本文件能长期不红的关键）**：
- **只写运行时可能送出的值**（整数）⇒ 字母码（`8A`）不是运行时输入，**不写进清单** ⇒ 它「运行时不可达」由脚本的可达性门禁守，不由清单守。
- **不逐条枚举码的含义** ⇒ 含义由字典定义（快照审），清单只钉**字典表达不了的不变量**：存量零破坏、台达修复、拆键效果、别名机制、未收录不编造。
- ⇒ **⇒ 清单会随内容迭代而失效的根因，是把「字典内容」抄进了「行为断言」** ⇒ 一旦发现清单要跟着字典改，说明该断言写错了层次。

| 断言 | 锁住什么 |
|---|---|
| 三菱若干条命中且含义不变 | **存量零破坏**（回归率 0） |
| 台达喂 `1` → 命中「过电流」 | **别名索引的先红后绿**（修前查不到，修后通）★ |
| `panasonic` 喂 `11` → 命中 A6 含义；`panasonic-a4` 喂 `11` → 命中 A4 含义；**两者不同** | **拆键效果** ★（A4 已拆出，A6 现场送 A4 的号会查不到而不是查错） |
| 同一含义的两种写法（数值身份 + 手册裸数字）命中同一条 | **别名机制**：现场两种写法都在 |
| 未收录的值 → `known=false` 且含义为空 | **不编造含义** |

## 9. 已知坑（实现时对照）

**坑 1（最可能让客户说「查不到」）：辅码与数值身份的口径**
- 松下 MINAS A6 是「主码.子码」，汇川是「三位主码 + 子码」⇒ 键 = 数值身份（`110` / `4100`），**不含辅码前缀**；主码相同、子码不同的变体**合并成一条**，子码差异写进 `cause`。
- 现场若把 `16.2` 当成 `162` 写 ⇒ 查不到 ⇒ `note` 必须写死「键 = 数值身份」。

**坑 2（最危险：不是查不到，是查错）：型号错配的兜底给错含义**
- 主 brand 键绑定某套码表；现场若是另一套（同号不同义），兜底会给错含义。
- 防线三层：① `note` 写明「本表对应 X 系列，若设备为 Y 请把 servo_brand 改为 `<brand>-<型号>`」；② 扩展 brand 键机制 + V3/G6 同步；③ 交付说明写清本轮收录的是哪一套、其余型号怎么办。

**坑 3（将来必踩）：支持字符串报警字 = 必须重设键形态**
- 本方案的键以「寄存器整数」为准。一旦支持字符串（能带前缀 `Er.410`），同一原始输入会归一化到两个不同的键 ⇒ **键方案必须重新设计** ⇒ 写进 ADR 作硬约束。

**坑 4：合并把子码差异抹平 ⇒ 按错相别排查**
- `E201.0/1/2/4` 合并后若 `cause` 不逐条写相别 ⇒ 维修工会按错相别去查（P 相过流去查 P 相，实际是 N 相）⇒ **合并时必须逐条列出子码含义**；黄金样本必须包含一个多子码合并项。

**坑 5：`displayCode` 抄错 ⇒ 界面显示一个手册里不存在的码**
- key 错是「查不到」（明显，维修工会反馈）；`displayCode` 错是「显示一个假码」（隐蔽，维修工照着它翻手册翻不到）⇒ **必须逐字抄手册，不许规范化**（`A.0b0` 的小写 b、`Err 11` 的空格都保留）⇒ 由基线快照 diff 审。

**坑 6：加载器 last-wins 静默覆盖**
- `brands.put(brand, m)` ⇒ 两个文件同 brand ⇒ 后者覆盖前者 ⇒ **一半码永远查不到，零报错** ⇒ G3 门禁 + 加载器对同 brand 第二个文件报错不覆盖。

**坑 7：别名覆盖已有键**
- 别名注册必须守卫「不得覆盖已有主键或别名」⇒ 否则 `"010"` 抢走 `"10"` ⇒ 给现场一个错含义。

**坑 8：按「手册数字段」推数值身份会跨族交叠 —— 必须用官方对象取值**
- 汇川 E 族主码三位（手册数字段 `410`）与 EA/EB/ED/EE 族主码两位（`03`/`05`/`09`/`11`/`20`）**数字段会重合** ⇒ 实测 **6 组**（`111`、`200`、`030`、`031`、`050`、`090`）⇒ **JSON 的重复键是静默覆盖 ⇒ 必然有一条被丢弃且零报错**。
- 安川更隐蔽：码是十六进制，`A.7A0` 的数字段是 `"7A0"`（里面的 A 是十六进制数字位，不是前缀）⇒ 「去掉所有字母」会把它变成 `70` ⇒ **15 组撞车**。
- ⇒ **正解（已落地）**：**数值身份 = 官方对象取值**（汇川与安川都是十六进制位值）⇒
  - 汇川：`E410` → `0x0410` = 1040；`EA33` → `0x0A33` = 2611；`EE08` → `0x0E08` = 3592 ⇒ **跨族区间不再交叠**（E 族 256..2452 vs aux 族 0..65）⇒ **不必拆 brand 键** ✓
  - 安川：`A.720` → `0x720` = 1824；`A.7A0` → `0x7A0` = 1952 ⇒ 零撞车 ✓
- ⇒ **纪律**：① 数值身份**按品牌分别定规则**（§2.6），**必须引用各自官方手册的对象取值列**，不得套用统一规则；② **脚本必须断言「同一 brand 内，数值身份唯一」**（G2）；③ **别名不得与主键或已注册别名冲突**（G5）—— PM 已在数据侧用脚本机械剔除，两处舍弃的别名（安川 `80`、汇川 `320`）已写进 note。
- ⇒ **判据一句话**：**键的合法性 = 「这个码的数值身份是否唯一、且这个数值在运行时唯一可达」。**

**坑 9（★ 本轮最该沉淀的一条）：「提高可达性」会把存量内容缺陷从「不可见」变成「可见」**
- 事实：台达 14 条的键是补零形态 ⇒ **在别名索引修复前，14 条全部不可达** ⇒ 表里 6 条**与官方手册不符的含义**（`AL008` 写成「位置控制误差过大」，官方是「异常脉冲控制指令」；`AL013` 写成「编码器数据异常」，官方是「紧急停止」；`AL015` 写成「驱动器过热」，官方是「正向极限异常」；`AL028` 写成「强制报警写入」，官方是「编码器内部错误」…）**一直是错的，但因为「查不到」，现场永远看不到 ⇒ **「查不到」把错误盖住了。**
- ⇒ **别名索引修通的那一刻，这 6 条的错含义第一次变成了现场会看到的错含义**（AL013 让人去动编码器、AL015 让人去清散热片）。
- ⇒ **纪律**：**任何让更多码变得可查的改动（别名索引 / 拆键 / 换键制 / 扩大收录范围），都必须先过一遍内容正确性核对** ⇒ 否则等于把「安全失败（查不到）」换成「危险失败（查错）」。
- ⇒ **⇒ 推论：ADR-D（修台达可达性）不是「零风险改动」，它是一次「内容体检」的触发器** ⇒ 这 6 条必须与可达性修复**同批修**（key / 别名 / `code()` 一律不动 ⇒ 命中行为与历史样本不断链，只改 `name`/`cause`/`remedy` 三个展示字段）。
- ⇒ **⇒ 通用判据**：**「查不到」是安全失败，「查错」是危险失败** ⇒ 任何内容缺陷的处理优先级，都高于功能扩展。

**坑 10：手册表的「名称列」与「详细名称」是两列，写错列就是把对的官方名称改错**
- 事实：三菱 MR-J4 §1.2 的报警表是「**名称** | **详细编号** | **详细名称**」三列 —— 报警号 `24` 的**名称列**是「主电路异常」（Main circuit error），而「伺服电机输出接地故障」是 `24.1` / `24.2` 的**详细名称**。
- ⇒ **把详细名称当名称写进 `name`，等于把官方手册里正确的名称改错**（现场拿手册一对照就对不上，反而更困惑）。正确做法：`name` = 名称列；`cause` = 详细说明（含 24.1/24.2 的区分）。
- ⇒ 同类风险：台达 ASDA-B2 的 `AL025`~`AL029` **五条官方名称完全相同**（都是 The Internal of the Encoder is in Error），只有中文细分不同 ⇒ **不能靠 name 区分，要靠 cause 里的中文细分区分** ⇒ 而 `AL030`（Motor Crash Error）是**另一个码**，最易与这五条写混。
- ⇒ **纪律**：收录时**先确定手册表的列结构**（名称列 / 详细编号列 / 详细名称列），再决定 `name` 放哪一列；同一官方名称对应多个中文细分时，**细分必须落到 `cause`**。
